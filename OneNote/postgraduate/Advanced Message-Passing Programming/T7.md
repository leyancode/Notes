主题一句话  
本段在对比传统 Point-to-Point 通信与 One-sided communications（单边通信）的背景与动机，说明为什么需要 RMA（Remote Memory Access，远程内存访问）以及它带来的同步挑战。  
核心逻辑讲解（连贯叙述）  
我们先问一个根本问题：为什么 MPI 要引入 One-sided communication？  
在传统的 Point-to-Point communications（点对点通信）中，通信必须是成对出现的。例如：
 
进程0 调用 MPI_Send  
进程1 必须调用 MPI_Recv
 
二者必须匹配（matching calls）。如果一方没有发起对应调用，通信无法完成。即便使用 MPI_ANY_SOURCE 或 MPI_ANY_TAG，接收方依然必须显式调用 MPI_Recv 才能参与匹配。  
这意味着什么？
 
第一，每个进程必须“知道”它可能会参与哪些通信。  
第二，通信需要 runtime 执行匹配逻辑。  
第三，程序员必须手动设计匹配结构。  
这种模型有一个本质特征：  
通信是“对称参与”的。

![Exported image](Exported%20image%2020260730161120-0.png)  
![Exported image](Exported%20image%2020260730161121-1.png)

但现代超级计算机网络通常支持 ==Remote Memory Access====（====RMA====，远程内存访问）硬件机制==。也就是说：  
一个进程可以直接读写另一个进程的内存。  
这带来了一个新可能：  
不再需要发送方和接收方同时调用匹配函数。  
发送方可以直接“写入”对方内存。  
优势是：

1. 省去 runtime 中的匹配开销
2. 编程模型更直接
3. 更贴近底层硬件能力

但是问题立刻出现：  
在 MPI_Send / MPI_Recv 中，同步是隐式的——双方调用就是同步点。  
而在 RMA 中：  
远程写（remote write）和远程读（remote read）没有天然的配对操作。  
==于是必须解决三个核心问题：==

1. ==什么时候目标进程允许别人访问它的内存？==
2. ==什么时候访问结束？==
3. ==如何保证一致性（====synchronisation====）？==

这就是 One-sided communication 的核心挑战。  
关键细节

1. Point-to-point 的本质￼通信双方必须都发起 MPI 调用。
2. One-sided 的本质￼发起方单独完成操作。
3. 最大问题￼同步不再天然存在，需要显式机制。
4. 后续章节结构提示￼如何通过 window、epoch 来建立安全访问区间。

1道练习题 + 分步骤答案  
题目  
为什么在 Point-to-Point 通信中，每个 MPI 进程必须“知道”它可能会参与哪些通信？  
分步骤答案  
第一步：Point-to-point 通信要求 matching calls  
MPI_Send 必须匹配 MPI_Recv。  
第二步：如果进程不知道会被发送数据  
它就不会调用 MPI_Recv。  
第三步：结果  
通信无法完成或导致死锁。  
结论  
因为通信是配对机制，双方都必须显式参与，因此每个进程必须提前设计好可能的 send/recv。
 
本段包括内容（动机 + 位置）  
这一段正式进入 One-sided communications 的工作机制部分，回答前一节提出的核心问题：在没有 send/recv 配对的情况下，MPI 如何建立安全、可控的远程内存访问？本段给出三个核心概念：origin、target、window、epoch，并说明基本执行流程和第一个同步机制 MPI_Win_fence。  
核心概念与直觉￼  
一、==origin== ==与== ==target==  
动机  
在 Point-to-Point 中，双方对称参与；在 One-sided 中，只有发起方主动操作。因此必须区分角色。  
定义  
==origin==：发起 RMA 操作的 MPI 进程（无论是读还是写）。  
==target==：其内存被访问的 MPI 进程。  
本质区别  
在 RMA 中，只有 origin 显式调用操作函数；target 不调用匹配读写函数。￼  
二、window（窗口）  
动机  
不能允许任意访问别人的整个地址空间。必须明确哪些内存是“可暴露”的。  
定义  
==window== ==是== ==MPI== ==进程对外暴露的一块内存区域。==  
只有在 window 中的内存，才允许被其他进程读写。  
直觉  
window = 可远程访问的受控共享区。￼  
三、==epoch====（访问阶段==）  
动机  
因为没有配对操作，必须人为定义一个“允许远程访问的时间区间”。  
定义  
==epoch== ==是允许== ==RMA== ==操作发生的时间段。==  
==只有在== ==epoch== ==内，====origin== ==才可以对== ==target== ==的== ==window== ==发起读写。==  
本质  
epoch = 同步区间。  
机制或流程  
整体执行流程可以抽象为以下顺序（每个进程都参与）：  
1 声明 window（collective）  
2 开始 epoch（collective，例如 MPI_Win_fence）  
3 在 epoch 内执行远程读写（MPI_Put / MPI_Get 等）  
4 结束 epoch  
5 释放 window￼￼

![Exported image](Exported%20image%2020260730161123-2.png)  

关键执行逻辑  
Declare window  
所有进程共同调用 MPI_Win_create  
Start epoch  
所有进程调用 MPI_Win_fence  
Issue RMA operations  
origin 发起远程读写（非阻塞）  
End epoch  
再次调用 MPI_Win_fence  
Free window  
MPI_Win_free￼  
重要说明  
==Remote-memory accesses== ==是== ==non-blocking====。==  
==也就是说，====MPI_Put / MPI_Get== ==调用返回时，操作可能尚未完成。==  
==完成保证依赖== ==epoch== ==结束同步。====￼==  
API / 规则速查  
一、声明 window  
函数原型  
==int MPI_Win_create==(  
void* base,  
MPI_Aint size,  
int disp_unit,  
MPI_Info info,  
MPI_Comm comm,  
MPI_Win* win  
);  
参数解释  
base  
已分配内存的起始地址。必须事先 malloc 或 static 分配。
 
size  
window 大小（字节数）。
 
disp_unit  
位移单位。origin 在指定偏移量时以该单位为基准。  
例如：  
若 disp_unit = sizeof(int)  
则 displacement = 3 表示偏移 3 个 int。  
前提：origin 和 target 的 int 大小一致。
 
info  
额外优化提示。
 
comm  
参与 window 的 communicator。
 
win  
输出的 window 对象。
 
关键语义  
MPI_Win_create 是 collective operation。  
所有 communicator 内进程必须调用。  
如果希望 MPI 自动分配内存，应使用 MPI_Win_allocate。￼  
二、启动 / 结束 epoch  
==MPI_Win_fence==(assert, win)  
语义  
第一次调用：开始 epoch  
第二次调用：结束 epoch，同时完成所有 RMA
 
MPI_Win_fence 是 collective。  
它同时承担：  
1 开始访问区间  
2 结束访问区间  
3 完成保证（completion）
 
常见坑  
1 忘记 collective 性质  
若某个进程不调用 MPI_Win_fence，会导致死锁。  
2 base 未分配内存  
MPI_Win_create 不会帮你分配。  
3 误以为 RMA 是 blocking  
读写完成依赖 epoch 结束。  
4 disp_unit 使用错误  
若 origin 和 target 数据类型大小不同，会产生错误偏移。
 
练习题 + 标准答案  
题目  
假设两个 MPI 进程共享一个 int 数组 arr[10]。  
使用 MPI_Win_create 暴露它。  
若 disp_unit = sizeof(int)，origin 想写入 arr[4]，应传递的 displacement 是多少？  
标准答案  
第一步  
displacement 单位是 disp_unit。  
第二步  
disp_unit = sizeof(int)  
第三步  
arr[4] 偏移 4 个 int  
因此  
displacement = 4  
如果 disp_unit = 1（字节），则 displacement = 4 * sizeof(int)。

核心概念与直觉  
一、MPI_Win_fence 的 assert 参数  
动机  
MPI_Win_fence 本身已经承担同步与完成语义，但在某些情况下，程序员可以“保证”某些行为不会发生，从而允许 MPI runtime 进行优化。  
本质  
==assert== ==不是语义改变，而是优化提示。==  
可组合方式  
可以使用逻辑或（bitwise OR）组合多个标志。
 
==MPI_Win_fence==(assert, win)  
四种主要断言  
1 MPI_MODE_NOSTORE  
含义  
自上次同步以来，本地 window 没有被本地 store、get 或 receive 更新。  
前提  
你真的没有写本地 window。  
优化直觉  
MPI 不需要处理本地缓存刷新。
 
2 MPI_MODE_NOPUT  
含义  
在本次 fence 之后直到下一次 fence 之前，本地不会发起 put 或 accumulate。  
前提  
当前 epoch 不发起写操作。  
优化直觉  
MPI 可以减少某些一致性处理。
 
3 MPI_MODE_NOPRECEDE  
含义  
本次 fence 不用于完成任何先前 RMA 操作。  
重要规则  
如果一个进程设置，所有进程必须都设置。  
语义  
表示这是“第一个 fence”。
 
4 MPI_MODE_NOSUCCEED  
含义  
本次 fence 不会开始任何新的 RMA 操作。  
同样是全组一致要求。  
语义  
表示这是“最后一个 fence”。  
关键理解  
NOPRECEDE → 不完成之前  
NOSUCCEED → 不开始之后  
它们分别作用在 fence 的“前半段”和“后半段”。
 
二、MPI_Put：写数据  
动机  
既然 window 已声明，epoch 已开始，那么如何真正写数据？  
定义  
MPI_Put 将 origin 缓冲区的数据写入 target 的 window。  
函数原型  
int MPI_Put(  
const void* origin_address,  
int origin_count,  
MPI_Datatype origin_datatype,￼

MPI_Datatype target_datatype,  
MPI_Win window  
);  
参数逻辑分解：
 
origin_address 本地数据起始地址。  
origin_count 本地元素个数。  
origin_datatype 本地数据类型。  
target_rank 目标进程编号。  
target_displacement 目标 window 内的偏移量。  
单位是 target 设置的 disp_unit。  
target_count 目标元素个数。  
target_datatype 目标数据类型。  
Window 关联的 window。
 
核心语义  
1 这是非阻塞操作。  
2 数据完成时间由 epoch 结束保证。  
3 origin 与 target datatype 必须类型兼容。  
重要前提  
必须处于合法 epoch 内。  
否则行为未定义。  
机制或流程
 
完整写操作流程  
1 MPI_Win_create  
2 MPI_Win_fence(0, win)  
3 MPI_Put(...)  
4 MPI_Win_fence(0, win)  
第二个 fence 结束时：

- 所有 put 操作完成
- 数据对 target 可见  
关键细节与语义  
1 target_displacement 的单位  
是 target 设置的 disp_unit。  
不是字节数。  
==2 origin_count== ==与== ==target_count==  
==必须匹配总数据量。==
 
3 assert 参数不改变程序正确性  
只影响优化。  
4 NOPRECEDE 与 NOSUCCEED  
若使用错误会导致未定义行为。  
常见坑  
1 在 epoch 外调用 MPI_Put  
2 误解 put 为 blocking  
3 disp_unit 理解错误  
4 某些进程设置 assert 但其他未设置（违反一致性要求）

核心概念与直觉  
一、MPI_Get：远程读取  
动机  
MPI_Put 是“我把数据写给别人”。  
MPI_Get 是“我从别人那里读数据”。  
在分布式内存模型下，默认不能直接读远程内存。  
RMA 提供一种受控方式允许 origin 主动读取 target 的 window。  
定义  
MPI_Get 从 target 的 window 中读取数据到 origin 的本地缓冲区。  
关键角色  
origin  
发起读取，并提供接收缓冲区。  
target  
提供被读取的 window 内存。￼

MPI_Win window  
);  
参数逻辑结构

本地接收缓冲区起始地址。  
origin_count  
本地接收元素个数。  
origin_datatype  
本地数据类型。  
target_rank  
目标进程。  
target_displacement  
目标 window 内偏移。  
单位由 target 的 disp_unit 决定。  
target_count  
目标元素个数。  
target_datatype  
目标数据类型。  
window  
关联的 window。
 
核心语义  
1 MPI_Get 是非阻塞的。  
2 实际数据到达由 epoch 结束保证。  
3 必须处于合法 epoch 内。  
与 MPI_Put 的对比
 
MPI_Put  
数据流向：origin → target  
MPI_Get  
数据流向：target → origin  
==但调用者始终是== ==origin====。==
 
机制或流程  
典型读取流程  
1 MPI_Win_create  
2 MPI_Win_fence(0, win)  
3 MPI_Get(...)  
4 MPI_Win_fence(0, win)

只有在第二个 fence 之后，origin 缓冲区的数据才保证有效。

2 origin_count × origin_datatype 的总大小

2 在第二个 fence 前访问 origin 缓冲区。  
3 disp_unit 单位理解错误。

本段包括内容（动机 + 位置）  
这一段进入 One-sided communication 的进阶能力：在远程写入的基础上支持 reduction 操作。核心问题是：当多个进程需要对同一个远程变量做累加等更新时，如何避免“读-改-写”的竞争与不一致？答案是 MPI_Accumulate。  
核心概念与直觉
 
一、常见场景：远程 reduction  
动机

![Exported image](Exported%20image%2020260730161128-4.png)

假设进程1有一个共享变量 V。  
进程0想对它执行 V = V + 1。  
朴素做法（naive approach）：  
步骤1  
MPI_Get 读取 V  
步骤2  
本地计算 V + 1  
步骤3  
MPI_Put 写回新值
 
问题在哪里？  
这是一个典型的 read-modify-write 模式。  
如果多个进程同时执行：  
1 进程A读到 V = 10  
2 进程B读到 V = 10  
3 两者都写回 11  
最终结果是 11，而不是 12。  
这就是数据竞争（race condition）。
 
根本原因  
Get 与 Put 是分离操作，中间没有原子性保证。
 
二、思想升级：Offloading reduction  
更好的方法是：  
不要自己做 read-modify-write，  
而是告诉 target “对这个值做一个 SUM”。  
也就是说，把 reduction 操作交给 MPI runtime 或底层网络。  
这就是 MPI_Accumulate。
 
定义  
MPI_Accumulate 将 origin 的数据与 target window 中的数据按给定运算 op 结合。  
本质  
它是带 reduction 操作的远程写入。

![Exported image](Exported%20image%2020260730161129-5.png)

三、MPI_Accumulate 机制  
函数原型

参数含义  
origin_address本地数据起始地址。  
origin_count  
本地元素个数。  
origin_datatype  
本地数据类型。  
target_rank  
目标进程。  
target_displacement  
目标 window 偏移（单位 disp_unit）。  
target_count  
目标元素个数。  
target_datatype  
目标数据类型。
 
op  
==reduction== ==操作，例如==  
==MPI_SUM==  
==MPI_MAX==  
==MPI_PROD== ==等==。
 
Win  
关联 window。
 
核心语义  
target_value = op(target_value, origin_value)  
而不是简单覆盖。  
例如：
 
==target_value = target_value + origin_value==
 
机制或流程  
典型 reduction 流程  
1 MPI_Win_create  
2 MPI_Win_fence  
3 MPI_Accumulate(..., MPI_SUM, ...)  
4 MPI_Win_fence  
在第二个 fence 后，结果保证一致。  
关键细节与语义  
1 MPI_Accumulate 是 RMA 操作，必须在 epoch 内。  
2 是非阻塞的，完成由同步保证。  
3 op 必须是 MPI 定义的合法 reduction 操作。  
4 datatype 必须支持该 op。  
5 origin_count 与 target_count 必须匹配。
 
最重要的区别  
MPI_Put 覆盖目标数据。  
MPI_Accumulate 组合目标数据。  
这使得 reduction 具有原子性保证（在同步语义下）。  
常见坑  
1 仍然使用 Get + Put 实现累加。  
2 op 与 datatype 不匹配。  
3 忘记同步导致读取旧值。  
4 target_displacement 单位误用。
 
练习题 + 标准答案  
题目  
三个进程同时对进程0的 window[2] 执行 +1。  
若使用 MPI_Get + MPI_Put，最终结果可能错误。  
为什么使用 MPI_Accumulate(MPI_SUM) 可以避免这个问题？  
标准答案  
第一步  
Get + Put 是分离操作。  
多个进程可能读取相同旧值。  
第二步  
写回时覆盖彼此结果。  
产生数据竞争。  
第三步  
MPI_Accumulate 将 reduction 操作交给 MPI 实现。  
MPI 在内部保证对目标数据的组合语义。  
结论  
MPI_Accumulate 提供原子式的 reduction 更新，避免 read-modify-write 竞争。

核心问题是：如何摆脱 fence 这种“全体同步”的粗粒度方式，实现更灵活、更局部的同步？  
核心概念与直觉  
一、MPI_Accumulate 的限制  
重要结论  
只能使用预定义的 reduction 操作。  
不允许 user-defined reduction。  
原因  
RMA 操作可能映射到底层网络硬件原子操作。  
硬件只支持标准操作（如 SUM、MAX 等）。  
因此：  
合法操作包括  
MPI_SUM  
MPI_MAX  
MPI_MIN  
MPI_PROD 等  
不能使用 MPI_Op_create 自定义运算。  
这是一个能力边界问题。
 
二、进一步解耦：Exposure 与 Access  
动机  
使用 MPI_Win_fence 时：

- 所有进程同时开始 epoch
- 所有进程同时结束 epoch
- 是 collective 操作

这种方式简单但限制太强。
 
因此引入两个概念：  
1 exposure epoch  
2 access epoch
 
定义  
==Exposure epoch==  
==某进程允许别人访问其== ==window== ==的时间区间。==  
==Access epoch==  
==某进程可以访问别人== ==window== ==的时间区间。==
   

关键理解￼  
在 fence 模型中：  
exposure epoch = access epoch  
并且所有进程同步开始与结束。
 
在 GATS 中：  
二者分离。  
并且起止操作分离。  
并且不再要求全体 collective。￼  
三、General Active Target Synchronisation（GATS）  
三个核心解耦目标  
1 解耦 exposure 与 access  
2 解耦 start 与 end  
3 解耦通信与 collective 操作  
直觉模型  
Origin 控制 access epoch。  
Target 控制 exposure epoch。  
两者通过匹配机制建立同步。

Target 进程：

==2 MPI_Win_post(group, assert, win) →== ==开始== ==exposure ep==och

1 MPI_Win_create

关键区别

避免额外同步检查。

题目  
为什么 GATS 相比 fence 更灵活？  
标准答案  
第一步  
Fence 是 collective。  
所有进程必须同步进入。
 
第二步  
GATS 分离 exposure 与 access。  
只在相关进程之间建立同步。

结论  
GATS 提供更细粒度、更局部的同步控制。

这一段把 GATS（General active target synchronisation）的“成套 API”补齐：target 侧用 MPI_Win_post / MPI_Win_wait 管 exposure epoch，origin 侧用 MPI_Win_start / MPI_Win_complete 管 access epoch，并给出 NOCHECK 断言及 complete/wait 的完成语义。核心是：用局部的匹配调用替代全体 fence，同步粒度更细。
 
核心概念与直觉  
一、GATS 的四个关键调用与角色分工  
动机  
fence 的问题是太“集体化”：所有进程必须一起同步。GATS 想做到：  
target 自己决定何时暴露内存（exposure epoch）  
origin 自己决定何时访问别人（access epoch）  
两者通过匹配机制对齐，而不是全体 barrier。
 
四个调用的配对关系  
先post后access
 
target 侧（暴露本地 window）  
1 ==MPI_Win_post(group, assert, win)==  
开始 exposure epoch  
group 指允许访问我的 origin 集合
 
2 MPI_Win_wait(win)  
结束 exposure epoch  
等所有匹配的 origin 完成访问
 
origin 侧（访问远程 window）  
1 ==MPI_Win_start(group, assert, win)==  
开始 access epoch  
group 指我将访问的 target 集合
 
2 MPI_Win_complete(win)  
结束 access epoch  
保证本 origin 这段 access epoch 内发起的 RMA 都在 origin 侧完成
 
直觉总结  
==post/wait== ==是== ==target== ==的====“====开门====/====关门====”==  
==start/complete== ==是== ==origin== ==的====“====进门====/====出门====”==  
门开着时，进门的人才能进行 Put/Get/Accumulate
 
机制或流程  
GATS 的最小闭环流程（仅就本段 API）  
Target（被访问方）  
1 MPI_Win_post(origin_group, assert, win)  
2 等待 origin 访问发生（期间 target 可以做别的事，但 window 暴露着）  
3 MPI_Win_wait(win)  
阻塞直到所有匹配 MPI_Win_complete 都发生  
返回时：这些 RMA 在 target window 上也已经完成
 
Origin（访问方）  
1 MPI_Win_start(target_group, assert, win)  
2 发起 RMA：MPI_Put / MPI_Get / MPI_Accumulate  
3 MPI_Win_complete(win)  
返回时：本 origin 在该 access epoch 内的所有 RMA 在 origin 侧都已完成  
关键完成语义（必须背住）
 
MPI_Win_complete 返回时  
origin 侧：该 access epoch 的所有 RMA 完成（completed at the origin）  
MPI_Win_wait 返回时  
target 侧：所有匹配 origin 都已 complete  
并且这些 RMA 在 target window 上也完成（completed at the target window）  
这两句话决定了你什么时候能安全读取/复用缓冲区、什么时候能确信远程更新已落地。

assert  
优化断言  
win  
window 对象
 
2 MPI_Win_start

group  
我将访问的 target 进程组  
assert  
优化断言

window 对象

语义  
完成 origin 侧该 access epoch 内的所有 pending RMA

语义

==关于== ==MPI_Win_start== ==的== ==NOCHECK== ==断言==

![Exported image](Exported%20image%2020260730161133-8.png)

MPI_MODE_NOCHECK（用于 start）  
含义  
当 origin 调用 MPI_Win_start 时，匹配的 MPI_Win_post 已经在所有 target 上完成。  
前提规则  
start 端能用 NOCHECK 当且仅当每个匹配的 post 也使用 NOCHECK。  
也就是说：双方必须一致。
 
直觉类比  
类似 ready-send 的“我确信对方已就绪，所以省一次握手”。  
但区别在于：这里 start 和 post 都必须声明 nocheck 才合法。  
常见坑（强相关）  
1 group 搞反  
post 的 group 是 origins  
start 的 group 是 targets  
方向错了就匹配不上  
2 以为 complete 等于“远程已经更新”  
complete 只保证 origin 侧完成。远程落地保证要看 target 侧 wait 返回。  
3 NOCHECK 单边使用  
会违反“必须双方一致”的规则，导致未定义行为。  
4 忘记 wait 会阻塞  
target 如果 wait 过早调用，可能会把自己卡住直到所有 origin complete。
 
练习题 + 标准答案  
题目  
在 GATS 下，进程0（origin）对进程1（target）的 window 执行 MPI_Put。问：  
哪个调用返回后，可以保证进程0的发送缓冲区可以安全复用？  
哪个调用返回后，可以保证进程1的 window 已经被更新完成？
 
标准答案  
第一问：保证 origin 缓冲区可复用  
MPI_Win_complete 在 origin 返回时，所有该 access epoch 内的 RMA 在 origin 侧完成。  
因此此时 origin 侧发送缓冲区可以安全复用。  
第二问：保证 target window 更新完成  
MPI_Win_wait 在 target 返回时，所有匹配 origin 都已 complete，且这些 RMA 在 target window 上完成。  
因此此时可以保证进程1 window 已完成更新。

核心概念与直觉  
一、Lock 的真实语义  
警告结论  
MPI_Win_lock 可能在真正获得锁之前就返回。
 
为什么？  
MPI 的同步保证发生在 MPI 语义层，而不是调用返回时就保证物理锁已获得。
 
MPI 只保证：  
在 MPI_Win_unlock 返回时，  
所有在该 lock/unlock 区间内发起的 RMA 操作已经完成。
 
换句话说：  
lock 不保证“立即独占”  
unlock 才保证“完成语义”
 
关键区别  
错误理解  
MPI_Win_lock 返回 = 我已经独占了目标 window  
真实语义  
MPI_Win_lock 返回 = 你已经进入一个访问 epoch  
但不保证此刻已经真正获得独占访问
 
真正的保证点在：  
MPI_Win_unlock 返回
 
二、为什么会这样设计？  
MPI 强调的是通信完成语义，而不是 OS 级别的互斥锁语义。  
MPI 保证：  
所有 MPI_Put / MPI_Get / MPI_Accumulate  
在 unlock 返回前完成。  
但 lock 本身不等价于立即获得排他执行权。
 
三、示例代码的关键陷阱  
代码

sleep(1);  
printf("MPI process %d says hi\n", my_rank);  
MPI_Win_unlock(...);
 
问题  
即便使用 MPI_LOCK_EXCLUSIVE，  
所有进程可能几乎同时打印。
 
原因  
printf 不是 RMA 操作。  
MPI 只对 RMA 调用施加同步保证。  
对普通计算或 I/O 没有排序保证。
 
结论  
lock 只对 RMA 内存访问建立语义约束。  
不是通用的分布式互斥锁。
 
四、Going even further：Flush 与 R 系列接口  
动机  
在 passive synchronisation 下，  
我们有时希望：  
不等到 unlock  
就确认某个具体 RMA 操作完成。
 
两类机制：  
1 Flush 操作  
用于强制完成远程操作（本页只提及概念）  
2 非阻塞 RMA 接口  
MPI_Rput  
MPI_Rget  
MPI_Raccumulate  
这些函数返回一个 request。
 
然后可以调用：  
MPI_Wait(request)  
来单独等待该 RMA 操作完成。  
核心思想  
从“epoch 级别完成”  
升级到  
“单个 RMA 操作级别完成”  
这提供更细粒度的控制。
 
关键细节与语义  
1 MPI_Win_lock 不保证立即获得独占访问。  
2 MPI_Win_unlock 返回时保证远程完成。  
3 printf 等普通代码不受 lock 排序约束。  
4 Rput/Rget/Raccumulate 提供 request 级别完成语义。  
5 passive synchronisation 中，所有同步由 origin 控制。  
常见坑  
1 把 lock 当成分布式 mutex。  
2 认为 lock 返回就意味着无其他并发访问。  
3 忘记 unlock 才是完成保证点。  
4 在 passive 模式下误解完成时机。

第一步  
lock 语义只约束 RMA 操作。  
第二步  
printf 不是 RMA 操作。  
第三步  
MPI 不保证普通计算或 I/O 的互斥顺序。

即使使用 EXCLUSIVE 锁，也不能用它来控制 printf 的执行顺序。
