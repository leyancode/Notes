**1. What is a Derived Datatype?****￼**

![Exported image](Exported%20image%2020260730160614-0.png)

**Definition**  
**A derived datatype** 是一种 **not predefined** 的数据类型。  
也就是说，它不是 MPI 标准中直接提供的内建类型。
 
**Simplified Definition**  
**A predefined datatype** 是具有 **predefined name** 的数据类型，例如：

- MPI_INT

==换句话说：==

- ==Predefined datatype====￼====MPI== ==已经定义好的基本类型==
- ==Derived datatype====￼====用户根据自身数据布局自定义的数据类型==
 
**Reference**  
相关正式定义可参考：

- MPI Standard Version 4.0
- Section 2.4.3

**2. Derived Datatypes Creation**  
**回顾：第一学期学过的** **datatype constructors**  
在 Semester 1 中已经学习过以下 MPI 派生数据类型构造函数：

- **MPI_Type_contiguous**
- **MPI_Type_vector**
- **MPI_Type_create_struct**

这些构造函数是理解更复杂 derived datatype 的基础。
 
**Vectors and Strides****￼**

![Exported image](Exported%20image%2020260730160615-1.png)

**MPI_Type_vector** **接口**  
int MPI_Type_vector(￼ int block_count,￼ int block_length,￼ int stride,￼ MPI_Datatype old_datatype,￼ MPI_Datatype *new_datatype￼);
 
**参数含义概览**

- **block_count****￼**==块的数量（====number of blocks====）==
- **block_length****￼**每个块中连续元素的个数
- **stride****￼**==相邻两个块起始位置之间的间隔==
- **old_datatype****￼**基础数据类型（已有 MPI datatype）
- **new_datatype****￼**新生成的 derived datatype
 
**关键问题：****What is the stride?****￼**

![Exported image](Exported%20image%2020260730160615-2.png)

**Question**  
In the datatype constructor MPI_Type_vector, what is the stride?  
**Definition**  
**Stride** ==是两个== ==consecutive blocks== ==的起始位置之间==，  
以 **old_datatype** **的元素个数** 为单位的距离。  
原文定义要点：  
==The stride is the number of elements between the start of two consecutive blocks.==  
重要补充理解：

- stride 不是 byte 数
- stride 的单位是 old_datatype 的个数
- stride 可以大于 block_length，从而形成 non-contiguous memory layout
 
**Intermediate Layers of Datatype Construction**  
在更高层的 datatype 构造中，MPI 提供了中间层构造函数：

- **MPI_Type_indexed**
- **MPI_Type_create_indexed_block**

这些函数用于描述更加不规则（irregular）的内存布局。
 
**Five Levels of Datatype Construction**  
MPI 中的派生数据类型构造可以理解为分层设计，从简单到复杂。

![Exported image](Exported%20image%2020260730160616-3.png)

**Level 1: MPI_Type_contiguous**  
**概念说明**  
**MPI_Type_contiguous**  
用于将已有 MPI datatype 连续重复 count 次，形成一个新的 datatype。  
特点：

- 数据在内存中是连续的
- 最基础、最简单的派生类型

示意理解：  
Int0 Int1 Int2 Int3 Int4 Int5 Int6 Int7 Int8
 
**MPI_Type_contiguous** **接口**

![Exported image](Exported%20image%2020260730160617-4.png)

int MPI_Type_contiguous(￼ int count,￼ MPI_Datatype old_datatype,￼ MPI_Datatype *new_datatype￼);
 
**Level 2: MPI_Type_vector**  
**概念说明****￼**

![Exported image](Exported%20image%2020260730160618-5.png)

**MPI_Type_vector** 在 contiguous 的基础上引入了 block 和 stride 的概念。  
核心思想：

- 每个 block 内是连续的
- ==block== ==与== ==block== ==之间可以有间隔（====stride====）==
- 用于描述规律性的 non-contiguous 数据布局

原文要点整理：

- vector is similar to contiguous
- repeats block_length times an existing MPI datatype
- repeats this block block_count times
- blocks are separated by stride
 
**对比总结：****contiguous vs vector****￼**

![Exported image](Exported%20image%2020260730160622-6.png)  

|   |   |   |
|---|---|---|
|**特性**|**MPI_Type_contiguous**|**MPI_Type_vector**|
|内存布局|完全连续|可非连续|
|block 概念|无|有|
|stride|不存在|存在|
|适用场景|简单重复|规则间隔数据|
   

**Five Levels of Datatype Construction****（续）**  
这一部分继续从 **MPI_Type_vector** 向更高层、更灵活的 datatype 构造方式推进。
 
**Level 2****（回顾）：****MPI_Type_vector****￼**

![Exported image](Exported%20image%2020260730160623-7.png)

**接口回顾**  
int MPI_Type_vector(￼ int block_count,￼ int block_length,￼ int stride,￼ MPI_Datatype old_datatype,￼ MPI_Datatype *new_datatype￼);  
核心特征总结：

- block_length 固定
- block_count 固定
- block 之间的间距由 stride 统一控制
- 适合 **规则（****regular****）** 的 non-contiguous memory layout
 
**Level 3: MPI_Type_create_indexed_block**  
**概念说明****￼**

![Exported image](Exported%20image%2020260730160624-8.png)

**MPI_Type_create_indexed_block**  
在 vector 的基础上进一步放宽限制：

- 每个 block 的长度仍然相同
- block 之间的间距不再固定
- 使用 displacements 明确指定每个 block 的位置

原文要点：  
indexed block is the same as vector, except that space between blocks can vary.
 
**接口定义****￼**

![Exported image](Exported%20image%2020260730160624-9.png)

int MPI_Type_create_indexed_block(￼ int block_count,￼ int block_length,￼ const int displacements[],￼ MPI_Datatype old_datatype,￼ MPI_Datatype *new_datatype￼);
 
**stride vs displacements****（非常重要）**  
这里是考试和理解中的关键区别。  
**stride****（在** **MPI_Type_vector** **中）**

- 表示两个 consecutive blocks 起始位置之间的距离
- 单位是 old_datatype 的元素个数
- 隐含顺序：block 必须按顺序排列

**displacements****（在** **indexed / indexed_block** **中）**

- 表示 datatype 起始地址到某个 block 起始地址的距离
- 单位同样是 old_datatype 的元素个数
- 每个 block 单独指定位置
 
**Be careful****（原文重点）****￼**

![Exported image](Exported%20image%2020260730160625-10.png)

- block 的位置不再由 stride 表达，而是由 displacements 显式指定
- displacements 是相对于 datatype 起始地址的 offset
- block 的顺序可以是 non-monotonically increasing
 
**Rationale****（设计动机）**

- blocks 可以以非单调顺序排列
- 例如：
    - 第一个 block 在内存中可以位于第二个 block 之后
- 提供了比 vector 更强的灵活性
 
**Level 4: MPI_Type_indexed**  
**概念说明**

![Exported image](Exported%20image%2020260730160626-11.png)

**MPI_Type_indexed** 是 indexed_block 的进一步扩展：

- block 之间的间距可以变化
- block_length 也可以变化

原文要点：  
indexed is the same as indexed block, except that block lengths can vary.
 
**接口定义**

![Exported image](Exported%20image%2020260730160627-12.png)

int MPI_Type_indexed(￼ int block_count,￼ const int block_lengths[],￼ const int displacements[],￼ MPI_Datatype old_datatype,￼ MPI_Datatype *new_datatype￼);
 
**关键特性总结**

- 每个 block 可以有不同的长度
- 每个 block 可以有不同的 displacement
- 能描述更加不规则（irregular）的内存布局
- 是 struct 之前的最后一层抽象
 
**Level 5: MPI_Type_create_struct**  
**概念说明****￼**

![Exported image](Exported%20image%2020260730160631-13.png)

**MPI_Type_create_struct** 是最通用、最灵活的 datatype 构造方式。  
原文要点（结合上下文理解）：  
==struct is the same as indexed, but datatypes can vary.==  
也就是说：

- block 长度可以不同
- block 位置可以不同
- 每个 block 的 datatype 也可以不同

示意：

- 一个 derived datatype 中可以同时包含：
    - Int
    - Double
    - 其他 MPI predefined 或 derived datatype￼

**Level 5: MPI_Type_create_struct**  
**接口定义**  
int MPI_Type_create_struct(￼ int block_count,￼ const int block_lengths[],￼ const MPI_Aint displacements[],￼ MPI_Datatype block_types[],￼ MPI_Datatype *new_datatype￼);
   
![Exported image](Exported%20image%2020260730160632-14.png)  

**参数含义说明**

- **block_count****￼**block 的数量
- **block_lengths[]****￼**每个 block 的长度（以 block_types[i] 为单位）
- **displacements[]****￼**每个 block 相对于 datatype 起始地址的偏移￼类型为 MPI_Aint（address integer）
- **block_types[]****￼**每个 block 对应的 MPI datatype￼可以是不同的 datatype
- **new_datatype****￼**新创建的 derived datatype
 
**设计层次总结（非常适合整理成一张表）**

|   |   |   |   |   |
|---|---|---|---|---|
|**Level**|**构造函数**|**Block** **长度**|**Block** **间距**|**Datatype** **是否可变**|
|1|MPI_Type_contiguous|固定|连续|否|
|2|MPI_Type_vector|固定|固定 stride|否|
|3|MPI_Type_create_indexed_block|固定|可变 displacements|否|
|4|MPI_Type_indexed|可变|可变|否|
|5|MPI_Type_create_struct|可变|可变|是|
    
**Five Levels****：一句话总结版**  
这一页给出了官方的高度概括版本，非常重要，建议原样记住逻辑结构。￼

![Exported image](Exported%20image%2020260730160633-15.png)

- **Contiguous****￼**Repeats X times type A.
- **Vector****￼**Repeats X times type A and calls that a block.￼Then repeats this block Y times, with a stride of Z.
- **Indexed block****￼**Same as vector, but space between blocks can vary.
- **Indexed****￼**Same as indexed block, but blocks length can vary.
- **Struct****￼**Same as indexed, but datatypes can vary.
 
**关键结论**  
在 MPI 中：

- **MPI_Type_create_struct is the most general type constructor**
- 其他所有构造方式在表达能力上都可以被 struct 覆盖
- 但 struct 并不一定是性能或可读性上的最优选择
 
**Five Levels** **的直观示意（理解用）****￼**

![Exported image](Exported%20image%2020260730160634-16.png)

- 前几层（contiguous → vector → indexed）￼主要处理的是：
    - block 重复方式
    - block 间距
    - block 长度
- struct 引入了新的自由度：
    - **datatype** **本身也可以变化**
    - 可以自然映射到 C struct / Fortran derived type
 
**Displacements** **问题（非常重要）****￼**

![Exported image](Exported%20image%2020260730160635-17.png)

**What if** **场景****￼**
 
假设 MPI 程序运行在两个不同体系结构的机器上：

- Machine A: int 占 2 bytes
- Machine B: int 占 4 bytes
 
**Consequence**  
如果 displacement 使用的是：  
3 * MPI_INT  
那么：

- 在不同机器上
- 实际 byte offset 会不同
- 导致 datatype 在 heterogeneous system 上不一致
 
**Heterogeneous Datatype Constructors**  
为了解决上述问题，==MPI== ==提供了== **heterogeneous datatype constructors**==。==  
这些构造函数的特点是：

- displacement 以 **bytes** 为单位
- 而不是以 old_datatype 的元素个数为单位
 
**常见的** **Heterogeneous Constructors****￼**

![Exported image](Exported%20image%2020260730160636-18.png)

- **MPI_Type_hvector**
- **MPI_Type_create_hindexed**
- **MPI_Type_create_hindexed_block**
- **MPI_Type_create_struct**
 
**Definition****（原文逻辑整理）**  
**A heterogeneous datatype constructor**  
是 datatype constructor 的一种变体，其中：

- displacements 以 **bytes** 表示
- 而不是以 number of elements 表示
 
**重要区分总结**

|   |   |
|---|---|
|**构造函数类型**|**displacement** **单位**|
|vector / indexed|number of elements|
|hvector / hindexed|bytes|

￼￼==“vector/indexed== ==的== ==displacement/stride== ==是按元素计；====hvector/hindexed/struct== ==是按字节计。====”==￼

MPI 提供了专门用于描述数组布局的构造函数：￼

![Exported image](Exported%20image%2020260730160637-19.png)

- **MPI_Type_create_subarray**
- **MPI_Type_create_darray**

典型应用场景：

- 多维数组
- 子数组（subarray）
- 分布式数组（distributed array）

这些在 stencil、domain decomposition 中非常常见。

**3. Derived Datatype Replication**
 
**背景问题：****Things do not go as planned****￼**

![Exported image](Exported%20image%2020260730160641-21.png)

**提问（回顾型问题）**  
Have you tried to use an MPI_Type_vector as part of an  
MPI_Scatter or MPI_Gather in last semester’s coursework?  
很多同学在实际使用中会遇到以下问题：

- 当尝试在 MPI_Scatter / MPI_Gather 中￼使用 **MPI_Type_vector**
- 尤其是试图“overlap vectors”时
- 程序行为异常，结果不符合预期，甚至直接错误
 
**根本原因（非常重要）**  
问题并不在于 Scatter 或 Gather 本身，而在于：

- **Derived datatype replication mechanism**
- 即 MPI 如何在内存中放置：
    - 同一 datatype 的第 1 个元素
    - 和第 2 个元素

一句话总结：  
MPI 在复制一个 datatype 时，  
并不是按“你直觉认为的数据布局”来做的，  
而是严格依赖 datatype 的 extent。
 
**Absolute Address vs Relative Address (Displacement)**  
在理解 replication 之前，必须先区分两个基本概念。

![Exported image](Exported%20image%2020260730160642-22.png)

**Absolute Address**  
**Definition**

- An **absolute address** 是程序中的一个真实内存地址
- 在实践中通常直接称为 address
 
**Relative Address (Displacement)**  
**Definition**

- A **relative address displacement****￼**是两个 absolute addresses 之间的差值

也就是说：

- displacement = address_B − address_A

在 MPI 中：

- displacement 通常用于描述￼block 相对于 datatype 起始位置的偏移

参考：

- MPI Standard v4.0
- Section 2.5.6
 
**Extent of an MPI Datatype****￼**

![Exported image](Exported%20image%2020260730160643-23.png)

**Definition****（核心定义）**  
**The extent of an MPI datatype** ==是：==  
==the distance between the first byte of data==  
==and the last byte of data, both inclusive.==  
也就是说：

- extent 覆盖了 datatype 所“占据”的整个内存区间
 
**Consequences of Extent****（极其重要）**  
**Consequence 1: Holes are included**  
对于 **non-contiguous datatypes**：

- extent **包含** **holes**
- ==holes== ==指的是：==
    - ==datatype== ==内部未使用==
    - ==但位于== ==first byte== ==和== ==last byte== ==之间的内存区域==

这点非常关键：

- MPI 在 replication 时￼会把整个 extent 当作一个整体
 
**Consequence 2: Trailing spaces are NOT included**

- ==extent== **不包括** **trailing spaces**
- ==也就是说：==
    - ==last byte== ==后面的空闲空间==
    - ==不属于== ==extent== ==的一部分==
 
**为什么** **replication** **会出问题**  
当 MPI 复制一个 datatype（例如 count \> 1）时：

- 第 n+1 个元素的起始地址 =
    - 第 n 个元素起始地址
    - 加上 **extent**

==如果== ==datatype== ==是== ==non-contiguous== ==的：==

- ==extent== ==可能比====“====实际数据量====”====大很多==
- ==中间包含== ==holes==

结果就是：

- datatype 被复制时
- 相邻元素之间的间距￼可能远大于你预期的间距
 
**与** **MPI_Scatter / MPI_Gather** **的关系**  
在 collective communication 中：

- ==MPI== ==会假设：==
    - ==buffer== ==中的元素是按== ==extent== ==顺序排列的==
- 而不是按你“视觉上理解的 block 排列”

因此：

- 使用 MPI_Type_vector 等 non-contiguous datatype
- 并尝试在 Scatter / Gather 中叠加使用
- 很容易由于 extent 问题导致错误结果
 
**本节小结（必须掌握）**

- Derived datatype replication 由 **extent** 决定
- extent：
    - 包含 holes
    - 不包含 trailing spaces
- MPI 在复制 datatype 时：
    - 不是压缩复制
    - 而是按 extent 跳跃
- 这正是：
    - MPI_Type_vector 在 collective 中“看起来坏掉”的原因
   

**Extent of an MPI Contiguous Datatype****（示例** **1****）****￼**

![Exported image](Exported%20image%2020260730160644-24.png)

**示例代码**  
int MPI_Type_contiguous(4, MPI_INT, &my_type);  
该语句创建了一个包含 **4** **个** **MPI_INT** 的 contiguous derived datatype。
 
**内存布局理解**  
Int0 Int1 Int2 Int3

- 数据是完全连续的
- 没有 holes
 
**Extent** **计算**

- **Extent(my_type) = 4 elements**
- ==这里的== ==elements== ==指== ==MPI_INT== ==的个数==

结论：

- 对 contiguous datatype
- extent 等于实际数据元素数量
 
**When things go well****（一切正常的情况）****￼**

![Exported image](Exported%20image%2020260730160645-25.png)

**场景设定**

- 2 个 MPI processes
- 一个 buffer，包含 8 个 integers
- 使用 **MPI_Scatter**
- 每个 process 接收一个 my_type
 
**数据分布示意（逻辑理解）**

- MPI0 接收：
    - Int0 Int1 Int2 Int3
- MPI1 接收：
    - Int4 Int5 Int6 Int7

原因：

- MPI 按 **extent(my_type)** 来划分 buffer
- 每次跳跃 4 个 elements
- 结果完全符合直觉
 
**We want more****（需求升级）****￼**

![Exported image](Exported%20image%2020260730160647-26.png)

**新需求假设**  
在不修改 MPI_Scatter 调用的前提下：

- 我们希望：
    - 每个 MPI process
    - 只接收到其子区间中的
        - 第一个 integer
        - 最后一个 integer
 
**约束条件**

- **MPI_Scatter** **必须保持不变**
- 只能通过修改 datatype 来实现

这正是 derived datatype replication 问题的核心应用场景。
 
**Extent of an MPI Vector Datatype****（示例** **2****）**  
**示例代码****￼**  
在 MPI_Type_vector 里，**stride** **的定义不是****“****两个** **block** **之间空出来的间隔（****gap****）****”**，而是：

- **stride =** **两个相邻** **block** **的****“****起始位置****”****之间相隔多少个** **old_datatype** **元素**
- 单位是 old_datatype 的元素个数（这里是 MPI_INT，所以单位是 int）

在图里的例子：
 
MPI_Type_vector(2, 1, 3, MPI_INT, &my_type);

- block_count = 2：2 个 block
- block_length = 1：每个 block 里有 1 个 int
- ==stride = 3====：第二个== ==block== ==的起点在第一个== ==block== ==起点之后第== ==3== ==个== ==int== ==的位置==

**Interleaving Datatypes****（问题开始出现）**  
**新的假设需求**  
如果我们希望：

- MPI0 和 MPI1 的数据 **交错（****interleaved****）**
- 而不是简单地：
    - 前 4 个给 MPI0
    - 后 4 个给 MPI1

例如：  
Int0 Int1 Int2 Int3 Int4 Int5 Int6 Int7￼MPI0: Int0 Int2 Int4 Int6￼MPI1: Int1 Int3 Int5 Int7
 
**关键问题**

- MPI_Scatter 默认：
    - 只按 extent 线性复制 datatype
- 它并不知道你“想要交错”
- 单靠 vector datatype：
    - 无法改变 replication 的步进方式
   

**Datatype Extent****（回顾与关键结论）****￼**

![Exported image](Exported%20image%2020260730160654-30.png)

- **The extent of types****￼**用于计算 **每个** **MPI process** **的** **displacement**
- **Changing the start****￼**如果希望改变 datatype 在 buffer 中“复制时的起点或步进方式”，￼就必须 **alter the extent**

一句话总结：  
MPI 中 replication 的步进完全由 extent 决定，  
想改变数据分布，就必须改变 extent。
 
**MPI_Type_create_resized****（关键工具）**  
**接口定义**

![Exported image](Exported%20image%2020260730160655-31.png)

int MPI_Type_create_resized(￼ MPI_Datatype old_datatype,￼ MPI_Aint lower_bound,￼ MPI_Aint extent,￼ MPI_Datatype *new_datatype￼);
 
**参数含义说明**

![Exported image](Exported%20image%2020260730160656-32.png)

- **old_datatype****￼**原始 MPI datatype（predefined 或 derived）
- **lower_bound****￼**新 datatype 的 lower bound￼暂时可以理解为 datatype 起始前的偏移￼本阶段通常设为 0
- **extent****￼**新 datatype 的 extent￼这是 replication 行为的关键控制参数
- **new_datatype****￼**存储新创建的 resized datatype
 
**为什么** **MPI_Type_create_resized** **能****“****拯救****”****我们**

- MPI 在 collective 中复制 datatype 时：
    - 不是复制“有用数据”
    - 而是按 **extent** 线性步进
- 对 vector / indexed 等 datatype：
    - extent 往往比实际数据大
- **MPI_Type_create_resized** 允许：
    - 保留 datatype 的内部结构
    - 但人为缩小或调整 extent
 
**Example****：使用** **MPI_Type_create_resized** **实现** **interleaving****￼**

![Exported image](Exported%20image%2020260730160657-33.png)

**原始** **vector datatype**  
MPI_Datatype my_vector;￼MPI_Type_vector(2, 1, 3, MPI_INT, &my_vector);  
含义：

- 选取 Int0 和 Int3
- 内部存在 holes
- 原始 extent = 4 * sizeof(int)
 
**创建** **resized datatype**  
MPI_Aint lower_bound = 0;￼MPI_Aint extent = sizeof(int);  
MPI_Datatype my_resized_vector;￼MPI_Type_create_resized(￼ my_vector,￼ lower_bound,￼ extent,￼ &my_resized_vector￼);￼MPI_Type_commit(&my_resized_vector);
 
**效果说明（非常重要）**

- 新 datatype：
    - 内部结构仍然是 vector
    - 但 extent 被缩小为 1 个 int
- 在 collective 操作中：
    - MPI 会按 sizeof(int) 步进
- replication 结果：
    - 数据将形成 **interleaved pattern**

结论：  
MPI_Type_create_resized 改变的是  
“datatype 之间的间距”，  
而不是 datatype 内部的布局。
 
**Lower Bound****（****lower_bound****）**  
**Definition****￼**

![Exported image](Exported%20image%2020260730160701-34.png)

**The lower bound of an MPI datatype**  
是 datatype 开始之前需要应用的 offset。
 
**Lower Bound** **的用途**

- 用于跳过：
    - headers
    - metadata
    - 对当前 MPI 操作无关的数据
- 本质作用：
    - 把 offset 融入 datatype 本身
    - 而不是在调用 MPI 函数时手动加指针偏移
 
**Lower Bound** **的直观理解（结构体示例）****￼**

![Exported image](Exported%20image%2020260730160702-35.png)

**示例结构体**

**需求示例**

- 希望对所有粒子的：
    - velocity_x
    - velocity_y
    - velocity_z
- 分别进行 MPI_Reduce
 
**传统做法（不推荐）**  
MPI_Reduce(all_particles + sizeof(double), ...);￼MPI_Reduce(all_particles + 2 * sizeof(double), ...);  
问题：

- 可读性差
- 易出错
- offset 分散在调用代码中
 
**推荐做法：使用** **lower bound****￼**

![Exported image](Exported%20image%2020260730160703-36.png)

- 构造一个 vector datatype：
    - block_count = 100
    - block_length = 1
    - stride = 3 doubles

    - 设置不同的 lower_bound

优势：

- offset 被封装进 datatype
- 代码更清晰、更安全
   

**Modularity and Maintainability**  
**设计问题背景****￼**

![Exported image](Exported%20image%2020260730160703-37.png)

考虑一个常见情况：

- 你在程序中定义了一个 struct
- 后续可能会：
    - 调整属性顺序
    - 在中间插入新的属性
    - 重构数据布局
 
**使用** **manual offset** **的问题**  
如果你在 MPI 调用中使用：

- 手动指针偏移
- 硬编码的 displacement

那么：

- 你必须在 **整个代码库中**
    - 找出所有相关 MPI 调用
    - 手动更新这些 offset
- 风险：
    - 极易遗漏
    - 隐蔽 bug
    - 维护成本极高
 
**使用** **lower bound** **的优势**  
如果 offset 被封装进：

- **MPI datatype definition**
- 并通过 **lower bound** 控制

那么：

- 当 struct 布局变化时：
    - 你只需要
        - 更新 datatype 的定义
        - 重新 commit
- MPI 调用代码：
    - 完全无需改动
 
**工程层面结论**

- **Manual offset**
    - 快速但脆弱
    - 不利于维护
- **Lower bound + derived datatype**
    - 模块化
    - 可维护
    - 可扩展
