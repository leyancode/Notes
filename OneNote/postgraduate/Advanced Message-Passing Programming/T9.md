主题一句话  
Hybrid Programming 指在同一程序中同时使用 **MPI****（分布式内存并行）** 和 **OpenMP****（共享内存并行）**，以适应现代超算的多层硬件结构。
 
核心讲解  
一 动机：为什么需要 Hybrid Programming  
现代超级计算机并不是简单的单层结构，而是具有明显的 **层级化硬件架构（****hierarchical hardware architecture****）**。  
例如典型 HPC 系统：  
节点层（node level）  
每个计算节点内部有大量 CPU cores，并共享同一块物理内存。  
系统层（cluster level）  
大量节点通过高速网络互联。  
以 EPCC 的超算 **ARCHER2** 为例：  
node 内部  
128 CPU cores / node  
系统规模  
约 5500+ nodes  
因此整体结构可以理解为：  
Supercomputer￼ ↓￼Many Nodes￼ ↓￼Many Cores per Node  
也就是说：  
系统既存在  
分布式内存并行  
Distributed Memory Parallelism  
也存在  
共享内存并行  
Shared Memory Parallelism
 
二 定义：Hybrid Programming 是什么  
Hybrid Programming（混合并行编程）指：  
在同一程序中同时使用  
MPI (Message Passing Interface)  
用于 **节点之间通信（****inter-node communication****）**  
OpenMP (Open Multi-Processing)  
用于 **节点内部线程并行（****intra-node threading****）**  
因此：  
MPI  
负责 **multi-node processing**  
OpenMP  
负责 **intra-node multi-threading****￼**  
整体模型可以写为：  
MPI + OpenMP  
在 HPC 中常被称为：  
MPI + X  
==其中== ==X== ==可以是==  
==OpenMP==  
==CUDA==  
==OpenACC==  
==SYCL== ==等==
 
三 机制：如何理解这种并行结构  
从执行结构来看：  
传统 MPI-only 模型：  
Node￼ ├─ MPI rank￼ ├─ MPI rank￼ ├─ MPI rank￼ └─ MPI rank  
==每个== ==core== ==运行一个== ==MPI process====。==(再这里，==core== ==就相当于一个====thread==,请记住)  
例如：  
128 cores / node  
→ 128 MPI ranks
 
Hybrid 模型：  
Node￼ ├─ MPI rank￼ │ ├─ OpenMP thread￼ │ ├─ OpenMP thread￼ │ └─ OpenMP thread￼ ├─ MPI rank￼ │ ├─ OpenMP thread￼ │ └─ OpenMP thread  
例如：  
每个 node  
4 MPI ranks  
每个 rank 32 threads  
则  
4 × 32 = 128 cores
 
四 关键理解  
课程这里强调一个重要事实：  
==即使== **硬件是多层结构**==，理论上仍然可以：==  
==每个== ==core== ==一个== ==MPI process==  
即：  
1 MPI process / core  
因此：  
==使用== **MPI-only** ==在技术上是完全可行的。==  
也就是说：  
Hybrid Programming  
并不是 **必须的**  
而是：一种 **优化策略（****performance optimisation strategy****）**  
用来更好地利用硬件层级。

核心问题：MPI-only solution 的挑战

==问题本质==

二 Load Balancing（负载均衡）  
问题本质  
MPI 进程之间：

主题一句话  
Hybrid MPI + OpenMP 程序的关键区别在于 **MPI** **初始化方式必须支持线程（****thread support****）**，因此使用 MPI_Init_thread 而不是 MPI_Init，并根据所需线程级别确定 MPI 与多线程之间的交互方式。
 
动机与位置  
在 Hybrid Programming 中：  
MPI  
负责 **process-level parallelism**  
OpenMP  
负责 **thread-level parallelism**  
因此一个 MPI 进程内部会运行 **多个线程**。  
这带来一个问题：  
MPI 是否允许 **多个线程调用** **MPI** **函数**？  
为了解决这个问题，MPI 提供了：  
MPI_Init_thread  
用于声明程序 **需要什么级别的线程支持**。
 
核心机制  
一 初始化阶段的变化  
传统 MPI 程序：  
初始化方式：  
==MPI_Init(&argc, &argv);==  
表示：  
==MPI== ==假设程序== **是单线程的**。
   

在 Hybrid 程序中：  
初始化方式变为：

==MPI_Init_thread(&argc, &argv, required, &provided);==  
==原因：==  
==程序可能使用==  
==OpenMP threads==  
==或其他线程模型。==
 
二 MPI_Init_thread 函数  
函数原型：  
int MPI_Init_thread(￼ int *argc,￼ char ***argv,￼ int required,￼ int *provided￼);  
参数解释  
argc 命令行参数数量  
argv 命令行参数数组  
Required ==程序== **请求的线程支持级别**  
Provided ==M====PI== ==实现== **实际提供的线程支持级别**

Hybrid 程序在结束时 **没有变化**。

因此：

结束保持不变。
 
线程支持等级（Thread Support Levels）  
MPI 定义了 **4** **个线程支持等级**。  
这些等级表示：MPI 是否允许 **多个线程调用** **MPI**。  
重要特点：  
这些等级 **按能力递增（****monotonically increasing****）**。  
也就是说：￼  
==MPI_THREAD_SINGLE====￼====\<====￼====MPI_THREAD_FUNNELED====￼====\<====￼====MPI_THREAD_SERIALIZED====￼====\<====￼====MPI_THREAD_MULTIPLE==
 
四个线程支持等级  
1 MPI_THREAD_SINGLE  
含义：  
MPI 进程 **只有一个线程**。  
即：  
no multithreading  
适用情况：  
MPI-only 程序。
 
2 ==MPI_THREAD_FUNNELED==  
含义：  
MPI 进程内部可以有多个线程，  
但 **只有主线程（****master thread****）可以调用** **MPI**==。==  
结构示意：  
MPI process￼ ├ master thread → MPI calls allowed￼ ├ worker thread￼ ├ worker thread￼ └ worker thread  
这是 **MPI + OpenMP** **最常见模式**。
 
3 MPI_THREAD_SERIALIZED  
含义：  
多个线程 **都可以调用** **MPI**，  
但 **不能同时调用**。  
必须保证：  
only one thread calls MPI at a time  
通常需要：  
==mutex / lock==
 
4 MPI_THREAD_MULTIPLE  
含义：  
多个线程可以 **同时调用** **MPI**。  
即：  
concurrent MPI calls allowed  
这是最强线程支持等级。  
但代价：  
==MPI runtime== ==需要复杂锁机制==  
性能可能下降
 
等级关系（重要考试点）  
四个等级满足：  
MPI_THREAD_SINGLE￼\<￼MPI_THREAD_FUNNELED￼\<￼MPI_THREAD_SERIALIZED￼\<￼MPI_THREAD_MULTIPLE  
因此可以使用比较运算符：  
if (provided \>= MPI_THREAD_FUNNELED)  
判断支持能力。
 
典型 Hybrid 程序初始化示例  
示例代码：  
int required = MPI_THREAD_FUNNELED;￼int provided;  
MPI_Init_thread(&argc, &argv, required, &provided);  
==if (provided \< required)== {￼ printf("Error: insufficient MPI thread support\n");￼ MPI_Abort(MPI_COMM_WORLD, 1);￼}  
逻辑解释  
1 请求 FUNNELED 线程级别  
2 MPI 返回实际支持等级  
3 如果支持不足  
4 终止程序
 
关键细节  
Hybrid MPI + OpenMP 最常见模式是：  
MPI_THREAD_FUNNELED  
原因：  
OpenMP master thread 调用 MPI  
其他线程执行计算  
结构：  
MPI process￼ ↓￼OpenMP parallel region￼ ↓￼master thread → MPI￼worker threads → compute  
这样：  
实现简单  
开销较低  
性能较好

这一段通过代码例子说明：**不同的** **MPI thread support level****，不是只看****“****有没有** **OpenMP”****，而是看****“****哪些线程会不会调用** **MPI****，以及是否会并发调用** **MPI”**。
 
动机与位置  
上一段已经定义了四种线程支持等级：  
==MPI_THREAD_SINGLE====￼====MPI_THREAD_FUNNELED====￼====MPI_THREAD_SERIALIZED====￼====MPI_THREAD_MULTIPLE==  
这一段开始进入真正容易出题、也最容易混淆的部分：  
同样都是 MPI + OpenMP 程序，  
到底该申请哪一个 thread level？  
判断标准不是“用了多少线程”，而是：  
1 哪些线程调用 MPI  
2 是否会有多个线程调用 MPI  
3 这些 MPI 调用是否可能同时发生
 
核心概念  
一 初始化时的标准检查模板  
课程给出的标准写法是：  
int required = \<your_value\>;￼int provided;  
MPI_Init_thread(&argc, &argv, required, &provided);  
if (provided \< required)￼{￼ printf("The threading support level required could not be met.\n");￼ MPI_Abort(MPI_COMM_WORLD, EXIT_FAILURE);￼}  
MPI_Finalize();  
逐行解释  
第 1 行  
int required = \<your_value\>;  
程序员指定自己需要的线程支持等级，例如：  
MPI_THREAD_FUNNELED  
或  
MPI_THREAD_SERIALIZED￼  
第 2 行  
int provided;  
用于接收 MPI 实现实际提供的支持等级。￼  
第 3 行  
MPI_Init_thread(&argc, &argv, required, &provided);  
初始化 MPI，并同时申请线程支持。￼  
第 4 行  
if (provided \< required)  
检查 MPI 实际提供的等级是否足够。  
前提：  
线程支持等级是单调递增的，即：  
MPI_THREAD_SINGLE￼\<￼MPI_THREAD_FUNNELED￼\<￼MPI_THREAD_SERIALIZED￼\<￼MPI_THREAD_MULTIPLE  
因此可以直接比较大小。  
第 5–8 行  
{￼ printf("The threading support level required could not be met.\n");￼ MPI_Abort(MPI_COMM_WORLD, EXIT_FAILURE);￼}  
如果不满足要求，就直接终止。  
原因是：  
线程支持不足时继续运行，可能导致错误行为或未定义行为。  
第 9 行  
MPI_Finalize();  
结束 MPI。这里与普通 MPI 程序相同。

作用：

三 Example of MPI_THREAD_SINGLE

![Exported image](Exported%20image%2020260730161204-2.png)

代码：  
void some_function(void)￼{￼ MPI_Send(...);￼ #pragma omp parallel￼ {￼ // Non-MPI code￼ }￼}  
代码解释  
第 3 行：  
MPI_Send(...);  
MPI 调用发生在 OpenMP 并行区之外。  
也就是说：  
调用 MPI 时，程序仍然是单线程执行。  
第 4–7 行：  
#pragma omp parallel￼{￼ // Non-MPI code￼}  
这里虽然创建了多个线程，但线程内部没有调用 MPI。  
因此整体语义是：  
MPI 调用只发生在单线程状态下。  
结论  
==这属于：==  
==MPI_THREAD_SINGLE==  
关键原因不是“程序完全没用线程”，而是：  
MPI 调用发生时，MPI 进程对 MPI 来说仍然是单线程使用的。

代码：

|master|只能 master thread 执行|
|==single==|==任意一个线程执行一次，不保证是== ==master thread==|

所以这里的关键问题是：  
MPI_THREAD_FUNNELED 的定义要求：  
只有 master thread 调用 MPI。  
而 #pragma omp single 只保证“一个线程执行”，不保证它是 master。  
结论  
严格来说，这段代码：  
不一定能算 MPI_THREAD_FUNNELED。  
因为如果执行 single 的不是 master thread，那么就违反了 FUNNELED 的要求。  
更稳妥的判断是：  
若 MPI 只允许 master thread 调用，则这里不安全。  
这一点是考试和代码审查中的高频坑。  
一句话记忆：  
master 一定是主线程  
single 只是某一个线程

|   |   |
|---|---|

主题一句话  
Hybrid MPI + OpenMP 虽然能缓解 MPI-only 的问题，但会引入新的复杂性，包括 **false sharing****、****NUMA** **绑定问题、多层同步语义以及并行度管理问题**，同时 MPI_THREAD_MULTIPLE 还可能带来明显性能损失。
 
动机与位置  
前面已经说明：  
Hybrid Programming 的目标是：  
减少 MPI processes  
利用 OpenMP threads  
但这带来了新的问题：￼  
MPI-only → process isolation  
Hybrid → threads share memory￼  
因此新的挑战主要来自：  
共享内存  
线程调度  
硬件拓扑
 
核心挑战￼  
一 False Sharing（伪共享）  
概念  
False Sharing 指：  
==多个线程访问== **不同变量**==，==  
==但这些变量位于== **同一** **cache line**==。==  
结果：  
CPU cache coherence 会不断失效并重新同步。  
示意：  
Cache line￼| varA | varB |  
Thread 1 writes varA￼Thread 2 writes varB  
虽然变量不同，但 cache line 相同。￼  
结果：  
cache line 在核心之间反复移动。  
为什么 Hybrid 更容易出现  
OpenMP threads共享同一地址空间。
 
而 MPI processes：  
each process → separate address space  
因此 MPI-only 程序天然避免 false sharing。  
例外：  
如果使用  
MPI-3 shared memory  
则仍然可能发生。
 
二 Process Mapping 与 Binding 更重要  
在 Hybrid 程序中：  
不仅需要考虑  
MPI process placement
 
还需要考虑  
OpenMP thread placement
 
两个概念：  
mapping  
进程映射到哪个 node / core
 
binding  
线程绑定到哪个 CPU core
 
问题  
如果绑定策略不好：  
线程可能访问远端内存。  
这会严重破坏：  
data locality
 
==NUMA== ==问题==  
现代 HPC 节点通常是：  
==NUMA architecture==  
==Non-Uniform Memory Access==  
结构：
 
NUMA region 0￼ cores￼ local memory
 
NUMA region 1￼ cores￼ local memory
 
如果线程访问跨 NUMA 内存：  
延迟显著增加。
 
三 Hybrid 配置复杂度增加
 
Hybrid 程序需要决定：  
MPI processes per node￼OpenMP threads per process
 
例如：  
一个 128-core node：  
方案 A  
128 MPI ranks￼1 thread each  
方案 B  
4 MPI ranks￼32 threads each  
方案 C  
8 MPI ranks￼16 threads each  
不同配置：  
性能差异巨大。  
因此 Hybrid 程序需要额外调优。
 
四 Synchronisation 粒度变化  
MPI 同步特点：  
==主要是== **point-to-point communication**  
例如：  
MPI_Send￼MPI_Recv  
同步粒度通常较粗。
 
OpenMP 同步特点：  
经常使用：  
#pragma omp barrier  
这是 **global barrier**  
即所有线程必须同步。  
Hybrid 程序中同时存在：  
process-level synchronisation  
thread-level synchronisation  
这就产生：  
multiple levels of synchronisation semantics
 
五 并行度结构变化  
MPI 程序通常遵循：  
SPMD Single Program Multiple Data  
含义： 所有 MPI processes **从头到尾并行执行**。
 
OpenMP 程序则不同：  
并行只发生在：  
#pragma omp parallel  
区域内。  
也就是说：  
serial code￼↓￼parallel region￼↓￼serial code￼↓￼parallel region  
==如果== ==parallel region== ==太少：==  
==线程利用率很低。==
 
六 Communication 与 Thread Overlap 更难  
MPI-only 程序中：  
可以设计  
computation￼overlap（==重叠==）￼communication  
例如：  
MPI_Isend￼MPI_Irecv  
Hybrid 程序中：  
需要同时考虑  
线程同步  
MPI 通信  
因此：  
overlapping inter-process and inter-thread  
变得更加困难。
 
七 MPI reduction worker 不参与问题
 
在 Hybrid 模式下：  
==MPI reduction== ==通常只由：== ==master thread== ==执行==。  
例如：  
MPI_Allreduce  
其他 worker threads 可能处于 idle 状态。  
因此：  
计算资源利用率可能下降。
 
优化建议（课程 Tips）  
一 NUMA-aware Hybrid 设计  
推荐策略：  
1 MPI process per NUMA region  
然后：  
spawn OpenMP threads￼to fill cores in that NUMA region  
结构示意：  
NUMA region￼ ↓￼MPI process￼ ↓￼OpenMP threads  
优点：  
避免 cross-NUMA memory access  
提高 locality
 
二 Thread-aware reduction  
如果 MPI reduction 成为瓶颈：  
可以自己实现：  
thread-aware user-defined reduction  
即：  
先在 OpenMP 内部 reduction  
再进行 MPI reduction
 
三 线程通信区分  
当多个线程与 MPI 交互时，  
需要区分消息来源。  
常见方法：  
使用 MPI tag  
MPI_Send(..., tag)  
或使用：  
different communicators  
例如：  
MPI_Comm_split  
来隔离通信。
 
Limitations（限制）  
最重要的一点：  
==MPI_THREAD_MULTIPLE==  
==通常性能较差。==  
原因：  
为了支持多个线程同时调用 MPI，  
MPI runtime 必须在内部加入：  
locks  
race-condition protection  
例如：  
每个 MPI 调用内部可能使用：  
mutex  
结果：  
每次 MPI 调用的开销增加。  
此外：  
有些 MPI 实现甚至 **不完全支持** **MPI_THREAD_MULTIPLE**。  
因此 HPC 实践中更常见的是：  
MPI_THREAD_FUNNELED  
或  
MPI_THREAD_SERIALIZED

2 NUMA memory locality  
3 MPI + OpenMP mapping configuration  
4 multi-level synchronisation semantics  
5 thread utilisation inside parallel regions  
6 MPI reduction worker idle  
7 MPI_THREAD_MULTIPLE performance penalty
