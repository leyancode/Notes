## 提示词正文（从这里开始复制）

你在 Obsidian 库 `E:\obsidian\algorithmDesign_ideas` 里工作，把 `OneNote\postgraduate\Advanced Message-Passing Programming\` 下的 OneNote 导出稿，改写成可长期复习、可考前速查的 Obsidian 笔记。

我每次指定一个源文件。只整理这一个文件，不提前展开后续讲次的内容。

### 一、原稿处理与路由

- **原始导出稿只读不改**，全部移动到 `原始稿件\` 子目录，保持原文件名。
- 整理版建在本目录下，通过 wiki 链接指回原始稿：`[[原始稿件/T7|T7 原始导出]]`。
- 文件命名统一为 `编号 + 空格 + 中文主题.md`，编号沿用讲次顺序：
  - 讲义：`01 课程导论.md` … `11 并行 IO.md`
  - 配套实验：在讲次号后加 `P`，如 `03P 派生数据类型实验.md`
  - 习题/考题：加 `Q`，如 `06Q 虚拟拓扑习题.md`
- 一讲内容过长（超过两屏）时，可拆成 `07.1`、`07.2`，但必须在 `07` 里留导航链接。

### 二、Obsidian 格式硬约束（最容易犯，输出前逐条自检）

**Callout 结构**：`> [!type]- 标题` 必须独占一行，正文另起一行以 `> ` 开头，中间隔一个 `> ` 空行。正文挤在标题行后面会导致折叠失效。唯一例外是顶部不折叠的 `> [!info] 知识图谱`，按库内既有写法，导航内容直接跟在下一行、不留空行。

```markdown
> [!tip]- 核心思路
> 
> 正文从这一行开始。
```

除顶部 `> [!info] 知识图谱` 不折叠外，所有详细内容 callout 一律带 `-` 默认折叠。类型只用这六种：

| 类型 | 用途 |
| --- | --- |
| `[!info]` 知识图谱 | 顶部导航：前置 · 同类 · 原始稿（不折叠） |
| `[!tip]-` 核心思路 | 为什么需要这个机制，它解决了什么麻烦 |
| `[!example]-` 示例推演 | 最小可复现例子 / 通信过程分步推演 |
| `[!success]-` 代码实现 | MPI 调用完整代码 + 参数含义 + 输入输出 |
| `[!warning]-` 易错点 | 说明错误**为什么**发生，不只列关键词 |
| `[!summary]-` 速查 | API 签名、参数表、性能结论 |

**Dataview 会劫持两种语法**（本库启用了 Dataview，写错会直接报错）：

1. 反引号代码段不能以 `=` 开头。`` `==` `` 会报 `PARSING FAILED`。单独提运算符改用行内公式 `$==$`；能带上下文就补全为 `` `count == 0` ``。加空格无效。
2. 正文不能出现裸露的 `::`。提到 `MPI::` 或 C++ 作用域时必须包进反引号，如 `` `std::vector` ``。

**其余格式**：

- 删掉 OneNote 导出的行尾双空格换行，改成正常空行分段。
- 修复被打烂的高亮语法（形如 `==A====（====B====）==`），改写成正常句子，需要强调时用 `**加粗**`，不要用 `==`。
- 公式一律 LaTeX：行内 `$T = t_{startup} + n \cdot t_{data}$`，独立公式 `$$...$$`。禁止 `\( \)`、`\[ \]`、HTML。
- 图片改用 Obsidian 内链 `![[文件名.png]]`，不要用 `![](Exported%20image%20....png)` 这种 URL 编码路径。
- **图片缺失时不要静默留断链**：源文件里引用的 `Exported image *.png` 在 `attachments\` 中大量不存在。找不到就删掉该链接，并按下一节的规则判断能不能用 mermaid 重建；重建不了的才进「待补」小节，列出：位置 + 这张图原本要说明什么 + 是否可用同目录的 `* - Ink.svg` 替代。

### 二·五、断图重建：先判断类型，再决定工具

**不要一律画成 mermaid。**按原图要表达的东西分流：

| 原图表达的是 | 用什么 | 说明 |
| --- | --- | --- |
| 谁在什么时刻调用了什么（通信时序、生命周期、握手过程、竞争条件） | `sequenceDiagram` | mermaid 最强的场景，往往比原截图更清楚 |
| 分支判断、模型选型、决策路径 | `flowchart TD` | 放在「考点归纳」里当判断路径用 |
| 参数表、断言表、语义对照 | **markdown 表格** | 已经是表格的不要画成图，那是倒退 |
| 数组下标、内存布局、偏移量 | **等宽 `text` 代码块画框线** | mermaid 画不了逐格数组，硬画很丑 |
| 代码截图 | **代码块** | 按原稿文字还原即可 |
| 概念比喻、纯示意 | 一句话或一行公式 | 别为画而画 |

mermaid 语法注意：

- 节点标签里出现中文标点、括号、斜杠时用双引号包住：`A["需要远程访问别人的内存"]`；flowchart 的边标签含逗号同样要引号。
- 换行用 `<br/>`，不要用真实换行。
- **不要写 `rect rgb(...)` 上色**——固定颜色在深色主题下会翻车，用 `Note over` 分隔段落代替。
- 异步 / 非阻塞调用用 `--)` 箭头，同步用 `->>`，正好对应 RMA 的非阻塞语义。

每重建一张图，都要在「待补」表里标出它替代了原稿哪一张，方便日后拿到课件时核对。

### 三、笔记骨架（固定顺序）

1. 第一行标签，与标题空一行
2. `> [!info] 知识图谱` 顶部导航
3. `# 编号. 主题：一句话说明`
4. 正文分节，每节保留 1～3 句可见结论，细节全部塞进折叠 callout
5. `## 一句话总结` —— 点破本质
6. `## API 速查` —— 本讲出现的 MPI 函数签名 + 参数 + 用途，表格形式
7. `## 知识图谱` —— 前置 / 同类 / 进阶的 `[[wiki-links]]`
8. `## 考点归纳` —— 触发信号 → 条件反射：题目出现什么描述时该想到本讲机制
9. `## 待补`（仅当有缺图或存疑内容时）

### 四、标签（第一行，kebab-case，不要发明集合外的标签）

```text
#course/ampp
#mpi/datatypes #mpi/collectives #mpi/topology #mpi/rma #mpi/persistent
#mpi/io #mpi/hybrid #mpi/performance #mpi/shared-memory #mpi/neighbourhood
#type/lecture | #type/practical | #type/exam
#status/todo | #status/review | #status/done
```

主题标签选 1～3 个最关键的，不堆叠。

### 五、写作要求

- 每个知识点按「动机（为什么需要）→ 本质（是什么）→ 用法（怎么用）」组织，先给结论再解释原因。
- 中文为主，关键术语保留英文并在首次出现时给中文解释，如「派生数据类型 derived datatype」。
- MPI 函数、变量名、类型名用反引号；代码注释用中文。
- 代码块必须带语言标识（`c` / `fortran` / `python`），包含必要的 `MPI_Init` / `MPI_Finalize` 边界。
- 较长代码不逐行解释，只说明：主流程、关键参数、通信语义、最易写错处。
- 性能相关结论必须写清前提（进程数、消息大小、网络假设），不给无条件断言。
- 涉及通信过程时用分步推演还原「谁在什么时刻做了什么」，不要只给一句抽象描述。

### 六、忠实性

- 只整理源文件里真实出现的内容，**不补充课件没讲的高阶知识**。
- 源文件表述矛盾或明显是导出错乱时，指出来并给出你的判断依据，不要静默改写。
- 信息不足时在「待补」里列出缺失清单，说明不同假设会导致的差异。
- 所有 `[[wiki-links]]` 必须指向真实存在的文件，写之前先确认；不存在的目标写成普通文本，不制造悬空链接。

### 七、输出前自检

- [ ] 每个 callout 的 `> [!type]- 标题` 独占一行，正文另起 `> ` 行

- [ ] 无行尾双空格；图片全部为 `![[...]]` 且文件真实存在，缺失的已进「待补」

- [ ] 标签在第一行且在合法集合内，与标题空一行
- [ ] 公式为 `$...$` / `$$...$$`
- [ ] 有「一句话总结」「API 速查」「知识图谱」「考点归纳」
