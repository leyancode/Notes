### 二、先清理原稿的脚手架（动笔前第一步）

源稿是 ChatGPT 逐段整理的产物，带一层**对复习毫无用处的结构性噪音**。这些必须全部删掉，不是「酌情保留」：

| 原稿里的东西 | 处理 |
| --- | --- |
| 「主题一句话」「本段包括内容（动机 + 位置）」「核心逻辑讲解」「关键细节」 | 删除标签本身，内容并入正文对应位置 |
| 「下一段建议」「后续章节结构提示」 | 全删。这是生成时的连续性提示，不是知识 |
| `> 来自 <chatgpt.com/...>` / Blackboard 链接 | 全删，在「待补」里记一笔出处存疑 |
| 行尾双空格换行 | 删掉，改成正常空行分段 |
| 被打烂的高亮 `==A====（====B====）==` | 改写成正常句子；需要强调用 `**加粗**`，不要恢复 `==` |
| 孤立的残留词、空标题 | 删除，在「待补」列出 |

**重复内容必须合并。** 源稿按段落生成，同一主题常被讲两遍甚至三遍（例：T7 里 GATS 的四个调用讲了两轮，第二轮才补上完成语义）。**不要照抄两遍**——把所有轮次的信息合成一节，取最完整的表述，缺的互相补齐。合并后如果发现两处说法冲突，按第六节「忠实性」处理。

### 三、Obsidian 格式硬约束（最容易犯，输出前逐条自检）

**Callout 结构**：`> [!type]- 标题` 必须独占一行，正文另起一行以 `> ` 开头，中间隔一个 `> ` 空行。正文挤在标题行后面会导致折叠失效。唯一例外是顶部不折叠的 `> [!info] 知识图谱`，按库内既有写法，导航内容直接跟在下一行、不留空行。

```markdown
> [!tip]- 核心思路
> 
> 正文从这一行开始。
```

除顶部导航外，所有内容 callout 一律带 `-` 默认折叠。类型只用这六种：

| 类型 | 用途 |
| --- | --- |
| `[!info]` 知识图谱 | 顶部导航：前置 · 后续 · 原始稿（不折叠） |
| `[!tip]-` 核心思路 | 为什么需要这个机制，它解决了什么麻烦 |
| `[!example]-` 练习 | 原稿的练习题 + 答案，同类合并成一条 |
| `[!success]-` 代码 | 函数原型 + 逐参数注释 + 核心语义 |
| `[!warning]-` 易错点 | 说明错误**为什么**发生，不只列关键词 |
| `[!summary]-` 速查 | 参数表、断言表、API 对照 |

**Dataview 会劫持两种语法**（本库启用了 Dataview，写错会在笔记里直接报红）：

1. 反引号代码段不能以 `=` 开头。`` `==` `` 会报 `PARSING FAILED`。单独提运算符改用行内公式 `$==$`；能带上下文就补全为 `` `count == 0` ``。加空格无效。**注意**：提到原稿里的高亮残留时也会踩这个坑，描述成「被高亮标记包裹的 xxx」而不是直接把 `==xxx==` 放进反引号。
2. 正文不能出现裸露的 `::`。含 `::` 的内容必须包进反引号，如 `` `std::vector` ``。

**其余格式**：

- 公式一律 LaTeX：行内 `$T = t_{startup} + n \cdot t_{data}$`，独立 `$$...$$`。禁止 `\( \)`、`\[ \]`、HTML。
- 图片用 `![[文件名.png]]`，不要 `![](Exported%20image%20....png)` 这种 URL 编码路径。
- 代码块必须带语言标识：`c` / `fortran` / `python` / `text` / `mermaid`。

### 四、断图重建：先判断类型，再决定工具

源稿引用的 `Exported image *.png` 在 `attachments\` 中**大量不存在**（该目录最新的导出图停在 2026-05）。断链一律删除，然后按原图要表达的东西分流。**不要一律画成 mermaid**：

| 原图表达的是 | 用什么 | 说明 |
| --- | --- | --- |
| 谁在什么时刻调用了什么（通信时序、生命周期、握手、竞争条件） | `sequenceDiagram` | mermaid 最强的场景，常比原截图更清楚 |
| 分支判断、模型选型、决策路径 | `flowchart TD` | 适合放进「考点归纳」当判断路径 |
| 参数表、断言表、语义对照 | **markdown 表格** | 已经是表格的别画成图，那是倒退 |
| 数组下标、内存布局、偏移量 | **等宽 `text` 块画框线** | mermaid 画不了逐格数组，硬画很丑 |
| 代码截图 | **代码块** | 按原稿文字还原即可 |
| 纯概念示意 | 一句话或一行公式 | 别为画而画 |

mermaid 语法注意：

- 节点标签含中文标点、括号、斜杠时用双引号包住：`A["需要远程访问别人的内存"]`；flowchart 边标签含逗号同样加引号。
- 换行用 `<br/>`，不要真实换行。
- **不要 `rect rgb(...)` 上色**——固定颜色在深色主题下翻车，用 `Note over` 分隔段落代替。
- 非阻塞调用用 `--)` 箭头，阻塞/同步用 `->>`，视觉上直接区分「调用返回」与「操作完成」。

**每张重建的图都要在「待补」表里标出替代了原稿哪一张**（用原文件名后缀如 `...161130-6`），方便日后拿到课件逐张核对。重建不了的标 ⬜，说明为什么还需要原图。

### 五、笔记骨架与折叠粒度

固定顺序：

1. 第一行标签，与标题空一行
2. `> [!info] 知识图谱` 顶部导航
3. `# 编号. 主题：一句话说明`
4. **开篇总览**：一段点破本讲要解决什么问题，加一张全局对照表（如三种同步模型的差异），然后 `---`
5. 正文分节 `## 一、…`
6. `## 一句话总结`
7. `## API 速查`
8. `## 知识图谱`
9. `## 考点归纳`
10. `## 待补`（有缺图或存疑时）

**折叠粒度**——这条决定笔记好不好用：

| 放在可见层 | 折叠进 callout |
| --- | --- |
| 每节 1～3 句结论 | 函数原型与逐参数注释 |
| **所有图**（mermaid / 等宽示意） | 参数表、断言表 |
| 关键对照表 | 易错点清单 |
| 一句话就能说清的核心语义 | 练习题与答案 |

**图不要折叠**。图的价值就是扫一眼看懂，折起来等于没有。折叠后整篇应该 1～2 屏读完。

`## API 速查`要**跨全篇汇总**，至少包含「是否 collective」和「完成语义」两列——这两列是考试里最常问、最容易混的。

`## 考点归纳`用「题目里出现这种描述 → 该想到什么」的两列表，末尾补一句本讲最集中的几类考法。

### 六、写作要求与忠实性

- 每个知识点按「动机（为什么需要）→ 本质（是什么）→ 用法（怎么用）」组织，先给结论再解释原因。
- 中文为主，关键术语保留英文并在首次出现给中文解释，如「派生数据类型 derived datatype」。
- MPI 函数、变量名、类型名用反引号；代码注释用中文。
- 并列结构优先转成对照表（如 Put vs Get、fence vs GATS vs passive），不要写成两段平行叙述。
- **完成语义、collective 性、单位这三类信息必须写死**：什么函数返回时保证了什么、谁必须一起调用、偏移量的单位是什么。这是本课程最大的失分点。
- 性能结论必须写清前提（进程数、消息大小、网络假设），不给无条件断言。
- 只整理源文件里真实出现的内容，**不补充课件没讲的高阶知识**；概念被提到但没给 API 的，注明「本讲只提概念，未给原型」。
- 源稿表述矛盾或明显是导出错乱时，**指出来并给出判断依据**，不要静默改写。例：原稿说「fence 第一次调用开始 epoch、第二次结束」，与同段「fence 同时承担开始、结束、完成保证」冲突——采用后者，并注明前者是针对单个 epoch 的简化说法，理由是 `NOPRECEDE`/`NOSUCCEED` 分管 fence 前后半段。
- 原稿的函数原型不完整（如只有裸参数名没有类型）时按 MPI 标准补齐，并在「待补」注明「若课件原型与此不符以课件为准」。
- 所有 `[[wiki-links]]` 必须指向真实存在的文件，写之前先确认；不存在的目标写成普通文本，不制造悬空链接。
