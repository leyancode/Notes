**3. Caution** **注意事项**  
Neighbourhood collective operations 本质上是 collective operations。  
这意味着：

- 必须由 communicator 中的所有 MPI processes 调用。
- 如果某些进程未调用，将导致程序错误或死锁。

换句话说：  
虽然它们只在“邻居”之间进行通信，但调用行为仍然是 collective 的。

**4.1 Situation** **场景问题**  
设想一个问题：  
每个 MPI process 持有一个数值，并希望计算其 neighbours 的数值之和。  
即：  
每个进程只对自己的邻居执行局部 reduction，而不是对整个 communicator 做 global reduction。
 
**4.2** **在** **MPI 3.0** **之前的做法**  
Before MPI 3.0：  
通常做法是：

- 创建多个 sub-communicators
- 在每个子通信器中执行 global reduction

这种方式存在问题：

1. MPI 并不是为成千上万个 communicators 设计的
2. 不同 communicator 之间的 collective operations 会产生 introduction delays
3. 没有 cross-communicator optimisation￼例如，一个 value 可能需要被传递到多个 sub-communicators 中

这会造成：

- 通信开销增大
- runtime 无法做全局优化
- 管理复杂度上升
 
**4.3 Topologies** **的作用**  
通过引入 topologies：

- MPI runtime 获得了完整的 connectivity information
- 可以明确每个进程的 neighbour 关系

在 MPI 3.0 中：  
引入了 neighbourhood collective operations。  
其核心思想是：  
只对每个 MPI process 的 neighbours 执行 reduction 或数据交换。
 
**4.4** **优势总结**  
使用 neighbourhood collective operations 的优点：

1. 不需要大量 sub-communicators
2. MPI runtime 可以根据拓扑信息进行底层优化
3. 支持更高效的局部通信模式
4. 更适用于 structured grids、Cartesian topologies 等应用场景

**2. Allgather**  
**2.1 MPI_Neighbor_allgather**  
**基本概念**  
MPI_Neighbor_allgather 类似于 MPI_Allgather，但区别在于：

- 数据只从 incoming neighbours 收集
- 而不是从 communicator 中的所有进程收集

也就是说：  
MPI_Allgather 是 global collective  
MPI_Neighbor_allgather 是 neighbourhood collective  
它只在拓扑中定义的邻居之间进行数据交换。
 
**2.2** **示例场景说明****￼**

![Exported image](Exported%20image%2020260730161034-0.png)

假设：

- 有 4 个 MPI processes
- 使用 graph topology
- 边为 undirected edges

注意：  
一个 undirected edge A — B  
等价于两个 directed edges：

- A → B
- B → A

这意味着通信是双向的。
 
**2.3** **通信过程分解**

![Exported image](Exported%20image%2020260730161035-1.png)  

**阶段** **1****：****Before exchange**

- 每个 MPI process 持有一个元素
- 假设四个进程分别持有：￼A, B, C, D
- 数据类型为某个 MPI datatype T

此时：  
每个进程仅持有自己的 sendbuf 内容。
 
**阶段** **2****：****During exchange**

![Exported image](Exported%20image%2020260730161035-2.png)

- 每个进程将自己的元素发送给所有 neighbours
- 同时从所有 incoming neighbours 接收数据

关键点：  
发送给每个 neighbour 的内容是相同的  
但接收的数据来自不同 neighbour
 
**阶段** **3****：****After exchange**

![Exported image](Exported%20image%2020260730161037-3.png)

交换完成后：

- 每个 MPI process 拥有来自所有 neighbours 的元素
- recvbuf 中按邻居顺序存储这些数据

注意：  
它不会收到非邻居进程的数据。

![Exported image](Exported%20image%2020260730161039-5.png)

**2.4** **与** **MPI_Allgather** **的对比**

|   |   |
|---|---|
|**操作类型**|**收集范围**|
|MPI_Allgather|所有 processes|
|==MPI_Neighbor_allgather==|==仅== ==neighbours==|

因此：  
通信规模从 O(P) 降为 O(degree)  
其中：  
degree = 当前进程在拓扑中的邻居数量  
对于规则网格，例如 Cartesian topology：

- 2D 网格内部点 degree = 4
- 边界点 degree = 2 或 3

这比全局通信更高效。

**2.6** **重要语义说明**

1. 它仍然是 collective operation￼communicator 中所有进程必须调用。
2. 每个进程：
    - 向所有 outgoing neighbours 发送数据
    - 从所有 incoming neighbours 接收数据
3. ==recvbuf== ==的大小应为：====￼====recvcount × indegree==

==其中：==  
==indegree = incoming neighbours== ==数量==
 
**2.7** **在** **HPC** **中的实际意义**  
在 stencil computation 或 domain decomposition 中：  
典型用途包括：

- halo exchange
- ghost cell update
- neighbour data sharing

与手动 MPI_Isend / MPI_Irecv 相比：  
优点：

- 语义更清晰
- 代码更简洁
- MPI runtime 可基于 topology 优化通信路径

**2.8 MPI_Neighbor_allgather** **的限制**  
MPI_Neighbor_allgather 有一个重要限制：

![Exported image](Exported%20image%2020260730161045-8.png)

==每个== ==MPI process== ==必须从每个== ==neighbour== ==接收相同数量的元素==。  
换句话说：

- recvcount 对所有 neighbour 是相同的
- 无法针对不同 neighbour 设置不同接收数量
- 无法设置不同的接收偏移

因此，它适用于：

- ==每个== ==neighbour== ==发送数据大小一致的场景==
- ==规则网格结构，例如固定大小== ==halo==
 
**2.9 MPI_Neighbor_allgatherv**  
为了提高灵活性，MPI 提供：  
MPI_Neighbor_allgatherv  
其特点是：  
==允许每个== ==neighbour====：==

- ==接收不同数量的元素==
- ==数据放置在== ==recvbuf== ==的不同位置==

也就是说：  
接收端可以对不同 neighbour 使用不同的 counts 和 displacements。

**参数说明**  
sendbuf  
发送缓冲区  
sendcount  
发送元素个数（对所有 neighbour 相同）  
sendtype  
发送数据类型  
recvbuf  
接收缓冲区  
==recvcounts[]==  
==数组，每个== ==neighbour== ==一个接收数量==  
displacements[]  
数组，每个 neighbour 在 recvbuf 中的偏移  
recvtype  
接收数据类型（对所有 neighbour 相同）  
comm  
带 topology 的 communicator
 
**2.11** **两种版本对比**

![Exported image](Exported%20image%2020260730161046-9.png)  

|   |   |   |
|---|---|---|
|**特性**|**MPI_Neighbor_allgather**|**MPI_Neighbor_allgatherv**|
|不同接收 counts|否|是|
|不同 displacements|否|是|
|不同 element types|否|否|

说明：  
No 表示所有 neighbour 使用相同值  
Yes 表示可以对不同 neighbour 使用不同值
 
**2.12** **重要注意事项**

1. ==发送端的== ==sendcount== ==是固定的====￼====不论是== ==allgather== ==还是== ==allgatherv====，都不能为不同== ==neighbour== ==指定不同== ==sendcount====。==
2. 目前不存在允许不同 element types 的 neighbourhood allgather 版本。

也就是说：  
recvtype 对所有 neighbour 必须一致。  
如果需要不同类型：  
通常应使用 MPI derived datatype 进行封装。
 
**2.13** **在实际** **HPC** **场景中的理解**  
在规则结构下，例如：  
==2D Cartesian topology== ==的内部点：==

- 上下左右 halo 大小相同
- 使用 MPI_Neighbor_allgather 即可

但在不规则结构，例如：

- 非均匀 domain decomposition
- 图结构负载不均

则：

- 不同 neighbour 可能需要传输不同大小数据
- ==应使用== ==MPI_Neighbor_allgatherv==
 
**2.14** **设计哲学总结**  
Neighbourhood collectives 的设计原则：

- 保持 collective 语义
- 利用 topology 信息
- 提供足够灵活性
- 但避免过度复杂接口

因此：

- 不允许不同 sendcount
- 不允许不同 element types
- 只允许接收端在 v 版本中调整布局

**3. Alltoall**  
**3.1 MPI_Neighbor_alltoall**  
**基本概念**

![Exported image](Exported%20image%2020260730161047-10.png)

MPI_Neighbor_alltoall 与 MPI_Neighbor_allgather 类似，但有一个关键区别：  
每个 MPI process 可以向不同 neighbour 发送不同的数据。  
对比：

- Neighbor_allgather：发送给所有 neighbour 的数据相同
- ==Neighbor_alltoall====：发送给每个== ==neighbour== ==的数据可以不同==
 
**3.2** **通信过程理解**  
假设：

- 每个进程有 degree 个 neighbours
- 每个 neighbour 对应一个独立的数据块
- 所有元素类型为某个 MPI datatype T
 
**阶段** **1****：****Before exchange**

![Exported image](Exported%20image%2020260730161048-11.png)

每个 MPI process：

- 为每个 neighbour 准备一个元素
- sendbuf 中按 neighbour 顺序排列

例如：  
如果某进程有 3 个 neighbours，则：  
sendbuf 包含 3 个元素，每个对应一个 neighbour。
 
**阶段** **2****：****During exchange**

![Exported image](Exported%20image%2020260730161048-12.png)

每个进程：

- 向每个 neighbour 发送对应位置的数据
- 从每个 neighbour 接收一个元素

注意：  
这里不是广播同一个值  
而是针对不同 neighbour 发送不同元素。
 
**阶段** **3****：****After exchange**

![Exported image](Exported%20image%2020260730161052-13.png)

交换完成后：

- recvbuf 中存储来自所有 neighbours 的数据
- 数据顺序与 neighbour 顺序一致
 
**3.3** **函数接口**

![Exported image](Exported%20image%2020260730161053-14.png)

int MPI_Neighbor_alltoall(￼ const void* sendbuf,￼ int sendcount,￼ MPI_Datatype sendtype,￼ void* recvbuf,￼ int recvcount,￼ MPI_Datatype recvtype,￼ MPI_Comm comm￼);
 
**3.4** **参数说明**  
==sendbuf==  
==发送缓冲区，包含针对每个== ==neighbour== ==的数据块==  
sendcount  
发送给每个 neighbour 的元素数量（相同）  
sendtype  
发送数据类型  
recvbuf  
接收缓冲区  
recvcount  
从每个 neighbour 接收的元素数量（相同）  
recvtype  
接收数据类型  
comm  
带 topology 的 communicator
 
**3.5** **与** **Neighbor_allgather** **的核心区别**

![Exported image](Exported%20image%2020260730161054-15.png)  

|   |   |   |
|---|---|---|
|**操作**|**发送数据**|**接收数据**|
|Neighbor_allgather|相同数据发送给所有 neighbour|相同数量|
|Neighbor_alltoall|不同数据发送给不同 neighbour|相同数量|

因此：  
Neighbor_alltoall 更适用于 halo exchange 中不同方向数据不同的情况。  
例如：  
在 2D Cartesian grid 中：

- 上方 neighbour 需要发送上边界
- 下方 neighbour 需要发送下边界
- 左右方向数据不同

这种场景更适合 Neighbor_alltoall。
 
**4. Ordering of neighbours**  
这是一个非常重要但容易忽略的概念。
 
**4.1** **邻居顺序的来源**  
Neighbourhood collective operations 依赖 communicator 中定义的 topology。  
邻居顺序由 topology 决定，而不是用户随意指定。  
不同 topology 的规则不同：

- Graph topology
- Cartesian topology
- Distributed graph topology
 
**4.2 Cartesian topology** **的顺序规则**  
对于 MPI_Cart_create 创建的 Cartesian topology：  
邻居顺序通常按维度排列：  
对于每个维度：

- 负方向 neighbour
- 正方向 neighbour

例如 2D 情况：  
假设维度为 (x, y)  
邻居顺序为：

1. x-
2. x+
3. y-
4. y+

这决定了：  
sendbuf 和 recvbuf 中数据的排列顺序。
 
**4.3** **为什么顺序很重要****￼**

![Exported image](Exported%20image%2020260730161055-16.png)

在 MPI_Neighbor_alltoall 中：  
sendbuf 是一个线性数组。  
MPI 根据 neighbour 顺序解释：  
sendbuf[i] 对应第 i 个 neighbour。  
如果顺序理解错误：

- 数据会发送给错误的 neighbour
- halo 更新错误
- 程序逻辑错乱
 
**4.4** **实践建议**  
在实际代码中：

1. 使用 MPI_Cart_shift 明确获取 neighbour rank
2. 打印 neighbour 列表进行验证
3. 明确记录 sendbuf 的逻辑顺序

例如：  
上、下、左、右顺序必须和 MPI 定义一致。
 
**4.5** **在** **HPC** **作业中的意义**  
在 stencil 或 domain decomposition 中：  
Neighbour ordering 直接决定：

- halo 数据布局
- ghost cell 更新顺序
- cache 访问模式

错误的 ordering 是 MPI 并行程序常见 bug 来源。
   

**3. Alltoall****（续）**  
**3.6 MPI_Neighbor_alltoall** **的限制**  
MPI_Neighbor_alltoall 要求：  
所有 MPI processes 必须向每个 neighbour 发送相同数量的元素。  
注意：  
这里的数量是以元素个数表示，而不是字节数。  
也就是说：

- ==sendcount== ==对所有== ==neighbour== ==相同==
- ==recvcount== ==对所有== ==neighbour== ==相同==
- ==sendtype== ==与== ==recvtype== ==固定==

适用于：

- 规则结构
- 每个 neighbour 数据大小一致
- 对称 halo 交换

为了支持不规则通信，MPI 提供：  
MPI_Neighbor_alltoallv  
其特点是：  
允许 sendcounts 和 displacements 变化  
允许 recvcounts 和 displacements 变化  
即：

- 不同 neighbour 可发送不同数量元素
- 不同 neighbour 数据可放置在不同内存位置

==但仍然限制：==

- ==所有== ==neighbour== ==使用相同== ==MPI_Datatype==

**参数说明**  
sendcounts[]  
每个 neighbour 的发送元素数量  
==sdispls[]==  
==每个== ==neighbour== ==在== ==sendbuf== ==中的偏移==

![Exported image](Exported%20image%2020260730161056-18.png)

alltoallv 仍然限制所有 neighbour 使用相同数据类型。  
为了支持不同 neighbour 使用不同类型，MPI 提供：

**3.9** **三种版本对比**  
**Neighbourhood Alltoall** **系列**

![Exported image](Exported%20image%2020260730161058-19.png)  

|   |   |   |   |
|---|---|---|---|
|**操作**|**Counts**|**Displacements**|**Types**|

**3.10** **选择建议**  
**使用** **MPI_Neighbor_alltoall**

- 每个 neighbour 数据大小相同
- 类型一致
- 规则网格

例如：  
均匀 2D 或 3D stencil。

![Exported image](Exported%20image%2020260730161101-20.png)

**使用** **MPI_Neighbor_alltoallv**

- 不同 neighbour 数据块大小不同
- 类型一致
- 不规则负载划分

例如：  
非均匀 domain decomposition。
 
**使用** **MPI_Neighbor_alltoallw**

- 不同 neighbour 需要不同 MPI_Datatype
- 使用 derived datatype 表示复杂结构
- 高度不规则图结构

例如：  
发送不同维度切片、不同结构体布局。
 
**3.11** **与** **Allgather** **系列的区别**  
Allgather：

- 每个进程发送一个数据块
- 接收来自 neighbour 的数据集合

Alltoall：

- 每个进程为每个 neighbour 准备独立数据块
- 是更一般形式

可以理解为：  
Allgather 是 Alltoall 的特例。
 
**3.12 HPC** **实际应用总结**  
在 stencil 计算中：

- 规则网格：使用 Neighbor_alltoall
- 不规则分块：使用 Neighbor_alltoallv
- 不同数据结构：使用 Neighbor_alltoallw

在高性能系统上：  
Neighbourhood collectives 优于手写 Isend/Irecv：

- runtime 可优化调度
- 减少通信管理开销
- 更清晰语义
   

**4. Ordering of neighbours**

![Exported image](Exported%20image%2020260730161103-21.png)

Neighbourhood collective operations 的一个核心问题是：  
邻居的顺序如何确定？  
因为：

- sendbuf 和 recvbuf 都是线性数组
- MPI 根据邻居顺序解释这些数组

如果顺序理解错误：  
数据将被发送到错误的 neighbour。
 
**4.1 Graph topology** **中的邻居顺序**  
**情况一：****使用** **MPI_Graph_create**
 
如果 communicator 是通过：  
MPI_Graph_create 创建的，  
那么：  
邻居的遍历顺序与创建时提供的邻接列表顺序一致。  
换句话说：  
邻居顺序由用户在构造 graph topology 时提供的数据结构决定。
 
**情况二：使用** **Distributed graph topology****（推荐）**  
如果 communicator 是通过：

**4.11 Cartesian topology** **中的邻居顺序**

![Exported image](Exported%20image%2020260730161108-26.png)  

在 MPI_Cart_create 创建的 Cartesian topology 中：  
邻居顺序具有明确规则。  
**规则一：按维度顺序遍历**  
Neighbours are iterated in order of the dimensions.  
也就是说：

- 先遍历第 0 维
- 再遍历第 1 维
- 依此类推
 
**规则二：每个维度中先负方向**  
In each dimension, the neighbour in the negative direction is selected first.  
因此：  
对于每个维度 d：  
顺序为：

1. 负方向 neighbour
2. 正方向 neighbour
 
**2D** **示例**  
假设 Cartesian topology 为 2D：  
维度顺序为 (x, y)  
邻居顺序为：

1. x-
2. x+
3. y-
4. y+
 
**3D** **示例**  
若为 3D：  
(x, y, z)  
邻居顺序为：

1. x-
2. x+
3. y-
4. y+
5. z-
6. z+
 
**4.12** **边界情况：****MPI_PROC_NULL**

![Exported image](Exported%20image%2020260730161112-27.png)

由于边界存在：  
某些 MPI processes 可能没有某个方向的 neighbour。  
例如：

- 左边界没有 x-
- 顶部没有 y+

此时：  
MPI 使用 MPI_PROC_NULL 作为占位。  
重要语义：  
Neighbourhood collective operation 的行为应当假定该 neighbour 存在。  
也就是说：

- sendbuf 和 recvbuf 必须仍然为该方向预留位置
- 即使 neighbour 是 MPI_PROC_NULL

否则：  
数组索引将错位。
 
**关键理解**  
即使某个方向没有真实 neighbour：  
buffer 结构必须保持完整维度顺序。  
例如：  
在 2D 中即使只有 3 个真实邻居：  
sendbuf 仍然应按 4 个方向组织。
 
**4.13 Non-blocking variants**  
Neighbourhood collective operations 也有 non-blocking 版本。  
与 point-to-point 通信类似：

- MPI_Send / MPI_Recv 是 blocking
- MPI_Isend / MPI_Irecv 是 non-blocking

Neighbourhood collectives 也是同样设计。
 
**4.14 Non-blocking** **语义**  
语义与常规 non-blocking 操作一致：  
buffers passed must not be overwritten until the corresponding request object has been waited upon.  
也就是说：

1. 调用 non-blocking 函数后立即返回
2. 不能修改 sendbuf 或 recvbuf
3. 必须调用 MPI_Wait 或 MPI_Test 等待完成

否则：  
会产生未定义行为。
 
**4.15 Blocking** **版本**

- MPI_Neighbor_allgather
- MPI_Neighbor_allgatherv

**4.16 Non-blocking** **版本**

![Exported image](Exported%20image%2020260730161114-29.png)

Non-blocking variants 包括：

- MPI_Ineighbor_allgather
- MPI_Ineighbor_allgatherv
- MPI_Ineighbor_alltoall
- MPI_Ineighbor_alltoallv
- MPI_Ineighbor_alltoallw

注意：  
函数名以 I 开头。  
典型接口形式为：  
int MPI_Ineighbor_alltoall(￼ ...,￼ MPI_Request* request￼);  
调用后：

- 返回 MPI_Request
- 后续需 MPI_Wait 或 MPI_Waitall
 
**4.17** **为什么使用** **Non-blocking** **版本**  
在 HPC 场景中：  
可以实现：  
communication-computation overlap  
例如：

1. 发起 Ineighbor_alltoall
2. 同时计算内部区域
3. 等待通信完成
4. 更新边界

这对于 stencil 计算至关重要。

Ordering of neighbours 的核心：

- Cartesian topology：按维度顺序，负方向优先

Non-blocking variants 的核心：

- 提供异步 neighbourhood collectives
- 语义与 MPI_Isend 相同
- 允许计算与通信重叠
