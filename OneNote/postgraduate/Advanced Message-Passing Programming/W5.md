**Meshes** **网格结构**  
**Structured meshes** **结构化网格**

![Exported image](Exported%20image%2020260730160847-0.png)

**Definition** **定义**  
**Structured mesh** 是一种网格结构，其中：

- 存在一种 **connectivity pattern****（连接模式）**
- 该连接模式 **对网格中的每一个元素都一致适用**

换句话说：  
每个 mesh element 的邻接关系遵循同样的规则。
 
**Important note** **重要说明**

- 网格本身在几何上可能是 **non-uniform****（非均匀）增长** 的￼例如为了适应边界条件（boundaries）
- 但即便如此￼网格中元素之间的 **连接方式（****connectivity****）仍然保持一致**

这也是 structured mesh 与 unstructured mesh 的本质区别之一。
 
**Typical communication patterns** **典型通信模式**  
**2D square mesh****（二位正方形网格）**

![Exported image](Exported%20image%2020260730160852-1.png)  
 -   
    
- 每个元素通常与其：
    - 上（north）
    - 下（south）
    - 左（west）
    - 右（east）￼进行通信
- 属于典型的 **nearest-neighbour communication pattern**
 
该模式在 finite difference、finite volume 方法中非常常见。
 
**2D hexagonal mesh****（二位六边形网格）**

![Exported image](Exported%20image%2020260730160853-2.png)  

- 每个元素具有 **6** **个相邻元素**
- 通信模式更密集
- 常见于某些物理模拟或特定几何离散场景
 
**Load-balancing** **负载均衡**  
在 **structured meshes** 中：

- Load-balancing 通常简化为一个核心问题￼即：

**如何在不同** **worker / process** **之间**  
**均匀分配** **mesh elements** **的数量**  
原因是：

- 每个元素的计算量相近
- 通信模式规则、可预测

因此负载不均通常直接来源于 **elements per worker** **不均衡**。

**Load-balancing** **负载均衡示例**

![Exported image](Exported%20image%2020260730160855-4.png)

**Case 1: 9 elements per MPI process**  
在该划分方式中：

- 每个 **MPI process** 被分配 **9** **个** **mesh elements**
- 这是一个理想化、均匀的负载分配示例

该示例用于说明：  
当 mesh 是规则且完整时，structured mesh 的负载均衡非常直接。
 
**Case 2: 6 elements per MPI process**

![Exported image](Exported%20image%2020260730160856-5.png)

在另一种划分规模下：

- 每个 **MPI process** 被分配 **6** **个** **elements**
- 同样保持了 **perfect load-balance**

这说明：  
在没有复杂几何约束的情况下，structured meshes 可以自然地实现均匀负载。
 
**Mesh with a “hole”** **含空洞的网格**  
**问题背景**

![Exported image](Exported%20image%2020260730160857-6.png)

当 mesh 中存在一个 **hole****（空洞）** 时：

- 某些 mesh elements 不再存在
- 原有的规则网格结构被破坏
- 负载均衡与通信模式开始变得复杂
 
**Mesh with a “hole”: basic partitioning**  
基础划分方式

![Exported image](Exported%20image%2020260730160858-7.png)

**方法说明**

- 仍然沿用原始的 **domain decomposition**
- 不对 mesh 的分区方式做额外修改
- hole 只是简单地“缺失”在某些 process 的区域中

![Exported image](Exported%20image%2020260730160902-8.png)

**Pros** **优点**

- No need to alter the underlying decomposition￼不需要修改原有的分解策略
- 实现简单
- 与原 structured mesh 代码高度兼容
 
**Cons** **缺点**

- Load-imbalance 明显存在

具体表现为：

- 3 个 MPI processes 各自拥有 **9 elements**
- 1 个 MPI process 仅拥有 **5 elements**

这会导致：

- 某些 processes 提前完成计算并 idle
- 整体并行效率下降
- Time-to-solution 由最慢的 process 决定
 
**Mesh with a hole: cyclic partitioning**  
循环划分方式

![Exported image](Exported%20image%2020260730160903-9.png)

**方法说明**

- 使用 **cyclic partitioning**
- 将 mesh elements 按照循环方式分配给 MPI processes
- hole 对应的缺失元素在全局范围内被“摊平”

![Exported image](Exported%20image%2020260730160904-10.png)

**Pros** **优点**

- Every MPI process is assigned 8 elements￼每个 MPI process 拥有 **完全相同数量（****8** **个）的** **elements**
- 实现了 **perfect load-balance**
- 有效消除了 element 数量不均的问题
 
**Cons** **缺点**

- Hindered data locality

具体含义：

- 相邻的 mesh elements 往往分布在不同的 MPI processes 上
- elements 在内存中 **rarely consecutive**
- 通信开销增加
- Cache locality 变差

因此：

- 负载均衡提升
- 但通信与内存访问效率可能下降
 
**小结** **Summary**  
在含 hole 的 structured mesh 中：

- **Basic partitioning**
    - 优点：简单，保持原有分解
    - 缺点：容易产生 load-imbalance
- **Cyclic partitioning**
    - 优点：负载完全均衡
    - 缺点：数据局部性差，通信成本高

**Mesh with a hole: more advanced partitioning**  
含空洞网格的高级划分方法  
**方法概述**

![Exported image](Exported%20image%2020260730160906-11.png)  

**More advanced partitioning** 介于：

- basic partitioning（简单但负载不均）
- cyclic partitioning（负载均衡但 locality 差）

之间，目标是在 **load-balance** 与 **data locality** 之间取得更优折中。
 
**Pros** **优点**

- Every MPI process has been assigned an identical number of elements (8)￼每个 **MPI process** 被分配到 **完全相同数量（****8** **个）的** **elements****￼**→ 实现了良好的 load-balancing
- Most elements are consecutive￼大多数 elements 在内存中是 **consecutive****（连续的）****￼**→ data locality 明显优于 cyclic partitioning
 
**Cons** **缺点**

- More complex￼划分策略本身更加复杂￼通常需要额外的算法或启发式方法
- Takes more time to complete￼划分阶段的计算成本更高￼preprocessing 时间增加
 
**小结**  
**Advanced partitioning** 的核心思想是：

- 不再追求“最简单”
- 也不单纯追求“完全平均”
- 而是综合考虑：
    - load-balance
    - memory locality
    - communication cost

这类方法在真实应用中非常常见。
 
**Limitations of structured meshes**  
结构化网格的局限性  
**优势回顾**  
Structured meshes 具有一些非常重要的优点：

- 存储方式规则
- indexing 简单
- connectivity 隐式、可推导
- 适合高效的 memory layout 与通信模式设计
 
**关键局限**

- Real-world meshes 往往更加复杂
- 很多真实问题 **无法自然分解为** **structured mesh**

这直接限制了 structured mesh 在工业与科研中的适用范围。

**Mesh partitioning** **网格划分问题**  
**核心问题：****What is the fitness function?**  
在进行 mesh partitioning 时，需要明确 **fitness function****（目标函数）**，可能包括：

- The number of cells per partition￼每个 partition 中的 cell 数量（load-balance）
- The connectivity of the partitions￼partition 之间的连接关系（通信量）
- How adjacent cells are￼相邻 cells 是否被分配在同一 partition 中（locality）
- Any “hole” to deal with￼是否存在 hole（空洞）
- Any disjoint partition to handle￼是否存在不连续（disjoint）的 partition
   

**Mesh partitioning** **网格划分**  
**What is the fitness function?**

![Exported image](Exported%20image%2020260730160914-16.png)

什么是划分的目标函数  
在进行 **mesh partitioning** 时，核心问题不是“如何切”，而是：  
**我们要优化什么？**  
常见的 fitness criteria 包括：

- The number of cells per partition￼每个 partition 中的 cell 数量￼用于衡量 load-balancing
- The connectivity of the partitions￼partition 之间的连接关系￼直接影响 communication volume
- How adjacent cells are￼相邻 cells 是否被分配在同一 partition 中￼关系到 data locality
- Any “hole” to deal with￼是否存在空洞区域需要处理
- Any disjoint partition to handle￼是否出现不连续（disjoint）的 partition
 
**Beyond static criteria** **超越静态指标**  
除了上述静态结构指标，还必须考虑：

- Communication patterns￼实际通信模式（谁和谁通信、频率如何）
- Execution flow￼程序执行流程是否同步、是否存在阶段性通信
- Variability of load-balancing at runtime￼运行时负载是否随时间变化

这意味着：

- mesh partitioning 本身是一个 **multi-objective problem**
- 很难通过单一指标给出“最优解”
 
**Partitioning: hard**  
网格划分是一个困难问题

![Exported image](Exported%20image%2020260730160915-17.png)

**事实总结**

- There exists multiple more advanced partitioning strategies￼存在大量高级划分策略

**Two-step view** **两阶段视角**  
通过 MPI，从数据到硬件的映射可以分为两步：

1. Decompose the data across MPI processes￼首先决定 **数据如何分配给** **MPI processes**
2. Map MPI processes onto the underlying hardware￼然后决定 **MPI processes** **如何映射到硬件资源**

这两个步骤是**逻辑上独立**的，但性能上高度相关。

**Virtual topology**  
**Definition** **定义**  
**Virtual topology** 指的是：  
The arrangement of MPI processes  
即：  
MPI processes 在一个抽象拓扑结构中的排列方式。  
该定义来自：  
MPI Standard version 4.0, Section 8.1
 
**Purpose of virtual topologies**

![Exported image](Exported%20image%2020260730160917-20.png)

为什么要使用虚拟拓扑  
**Question**  
Why do we use virtual topologies?
 
**Reason 1: Programmer convenience**  
提升程序员的表达能力

- Virtual topologies 提供更直观的抽象
- 例如在 **Cartesian virtual topology** 中：
    - 使用坐标而非 rank
    - 通过 shift 直接找到邻居 process

这使得：

- 程序逻辑更接近问题本身的几何结构
- 代码可读性和可维护性显著提高
 
**Reason 2: Informing the MPI runtime**  
为 MPI runtime 提供通信信息

- Virtual topologies 向 MPI runtime 描述：
    - 通信模式
    - process 之间的逻辑邻接关系
- MPI runtime 可以利用这些信息：
    - 改善 MPI process 到硬件的 placement
    - 减少通信延迟
    - 提升整体性能
 
**Hardware considerations** **硬件层次因素**

![Exported image](Exported%20image%2020260730160918-21.png)

在实际系统中，MPI runtime 需要考虑多层硬件结构：

- 一个 MPI process 对应一个 software thread
- Software thread 最终运行在 hardware thread 上
- 多个 hardware threads 可能：
    - 位于同一 core
    - 共享 cache（通常是 L3）
- 多个 cores 可能：
    - 位于同一 processor
    - 访问同一 NUMA memory region
- 不同 processors：
    - 位于不同 nodes
    - 不同 nodes 位于不同 racks
 
**Why virtual topologies help**  
通过声明 **virtual topology**：

- MPI runtime 获得额外的结构信息
- 可以做出更合理的：
    - process placement
    - communication-aware mapping

说明：  
此处暂不考虑 hybrid programming（MPI + OpenMP）。

- 根据 connectivity 信息
- 构建合适的 **virtual topology**

    - Cartesian topology
    - 或 graph topology

**MPI_Cart_create**  
创建 Cartesian 虚拟拓扑  
**函数原型**

![Exported image](Exported%20image%2020260730160925-26.png)

int MPI_Cart_create(￼ MPI_Comm old_communicator,￼ int dims_count,￼ const int dims[],￼ const int periods[],￼ int reorder,￼ MPI_Comm new_communicator￼);
 
**参数说明（概念层面）**

- old_communicator￼原始 communicator（通常是 MPI_COMM_WORLD）
- dims_count￼维度数量（如 2D、3D）
- dims[]￼每个维度上的 process 数量
- periods[]￼每个维度是否 periodic￼用于表示环状连接
- reorder￼是否允许 MPI runtime 重新排列 rank
- new_communicator￼返回的 Cartesian communicator
 
**Reordering**  
进程重排

- reorder 参数：
    - 允许 MPI runtime 改变 MPI rank 的映射关系
- 目的：
    - 更好地匹配底层硬件拓扑
    - 减少通信延迟

结论：  
Reordering **can have an impact on performance**。  
这也是 virtual topology 不只是“语法糖”的关键原因之一。
 
**MPI_Dims_create**  
自动寻找维度划分  
**函数原型**

![Exported image](Exported%20image%2020260730160926-27.png)

int MPI_Dims_create(￼ int process_number,￼ int dims_count,￼ int dims[]￼);  
**作用**

- 给定：
    - 总 process 数
    - 维度数
- 自动计算一个：
    - 尽量“均衡”的 Cartesian 维度划分

常用于：

- 不想手动计算 dims
- 希望得到较为合理的默认拓扑结构
 
**MPI_Cart_shift**  
查找邻居进程  
**函数原型**

![Exported image](Exported%20image%2020260730160927-28.png)

int MPI_Cart_shift(￼ MPI_Comm communicator,￼ int direction,￼ int displacement,￼ int* source,￼ int* destination￼);  
**作用**

- 在 Cartesian topology 中：
    - 沿某一维度（direction）
    - 偏移 displacement
- 返回：
    - source rank
    - destination rank

这是 **nearest-neighbour communication** 中最常用的接口之一。

**MPI_Graph_create**  
**核心思想**

![Exported image](Exported%20image%2020260730160935-34.png)

使用 MPI_Graph_create 创建 graph topology 时：

- **每一个** **MPI process** **都必须提供整个** **graph** **的完整描述**
- ==即：==
    - ==所有== ==nodes==
    - ==所有== ==edges==
- ==这是一个== **fully replicated graph description**

==这也是它在大规模系统中可扩展性有限的原因之一。==
 
**函数原型**  
int MPI_Graph_create(￼ MPI_Comm old_comm,￼ int number_of_nodes,￼ const int indexes[],￼ const int edges[],￼ int reorder,￼ MPI_Comm* new_comm￼);

![Exported image](Exported%20image%2020260730160935-35.png)  

**参数概览（逻辑层面）**

- old_comm￼原 communicator，通常是 MPI_COMM_WORLD
- number_of_nodes￼graph 中的节点数量￼通常等于 MPI process 数
- indexes[]￼描述每个节点邻居数量的前缀和数组
- edges[]￼存储 graph 中所有 edges
- reorder￼是否允许 MPI runtime 重排 ranks
- new_comm￼返回的 graph communicator
 
**MPI_Graph_create: the indexes parameter**  
**indexes** **的含义**

![Exported image](Exported%20image%2020260730160939-36.png)

==indexes[]== ==是一个== **prefix sum array**==，用于描述：==  
==对于== ==rank ≤ i== ==的所有== ==MPI processes====，==  
==其邻居总数的累积值。==  
也就是说：

- indexes[i]￼表示 ranks 0 到 i 的所有 neighbours 数量之和
 
**示例说明**

- indexes[3]（C 语言）
- 或 indexes(4)（Fortran，1-index）

必须等于：

- MPI process 0、1、2、3
- 所有 neighbours 的 **总数量**
 
**设计目的**  
这种设计使得 MPI 可以：

- 精确知道 edges[] 中需要读取多少条记录
- 从而正确解析整个 graph
 
**MPI_Graph_create: the edges parameter**  
**edges** **的含义**  
edges[] 数组：￼

![Exported image](Exported%20image%2020260730160940-37.png)

- 包含 graph 中的 **所有** **edges**
- 按 **source rank** **顺序** 存储

重要特性：

- Edges 是 **undirected**
- 不需要为同一连接指定两个方向
- **Redundant edges** 和 **self edges** 都是允许的

![Exported image](Exported%20image%2020260730160941-38.png)

**示例说明**  
假设：

- MPI process 0 连接到 1、3、4
- MPI process 1 连接到 2、4

则：  
edges = {1, 3, 4, 2, 4}

最终生成一个 **graph communicator**，其逻辑连接关系由该 graph 定义。

**Scalability issue of MPI_Graph_create**  
MPI_Graph_create 的可扩展性问题

![Exported image](Exported%20image%2020260730160951-44.png)

**根本问题**  
MPI_Graph_create 的设计要求：

- **每一个** **MPI process** **都必须：**
    - 存储整个 graph
    - 通过网络传递整个 graph
 
**极端示例说明**  
假设：

- Graph 包含 **100 billion edges**
- 需要约 **1 TB RAM** 才能存储完整 graph

则意味着：

- 每个 MPI process 都需要 1 TB 内存
- 每个 MPI process 都要传输 1 TB 的 graph 数据
 
**关键结论**

- 即使使用：
    - ARCHER2 的 700,000+ cores
- 也 **无法解决问题**

原因是：

- graph **没有被分布式存储**
- memory bottleneck 在单个 process 上依然存在

- 每个 MPI process：
    - 只描述 graph 的一部分
    - 而不是整个 graph

**MPI_Dist_graph_create_adjacent**

![Exported image](Exported%20image%2020260730161013-60.png)

基于相邻关系的分布式图拓扑创建  
**设计动机**

- MPI_Dist_graph_create：
    - 提供 **最大灵活性**
    - 任何 process 都可以指定任意 edge
- 但问题在于：
    - 涉及到某条 edge 的其他 MPI processes
    - 必须被“告知”这些拓扑信息
    - 因此仍然需要通信
 
**MPI_Dist_graph_create_adjacent** **的思想**  
第三种方式是：  
**MPI_Dist_graph_create_adjacent**  
其核心约束是：

- 每个 MPI process：
    - **只指定包含自身的** **edges**
    - 不描述与自身无关的连接关系

这样做的结果是：

- 进一步减少拓扑构建阶段的通信
- 语义更贴近“局部视角”的 graph 描述
 
**三种** **graph topology** **创建方式对比（逻辑总结）**

- **MPI_Graph_create**
    - 每个 process 提供完整 graph
    - 简单直观
    - 不可扩展
- **MPI_Dist_graph_create**
    - Graph 分布式构建
    - 灵活、可扩展
    - 但仍需要协调 edge 信息
- **MPI_Dist_graph_create_adjacent**
    - 每个 process 只描述自身相关 edges
    - 最贴近局部通信模式
    - 构建开销最低
   

**MPI_Dist_graph_create_adjacent**  
基于相邻关系的分布式图拓扑创建

![Exported image](Exported%20image%2020260730161014-61.png)

**设计定位**

- MPI_Dist_graph_create_adjacent 是 **第三种** 创建 graph virtual topology 的方式
- 相比：
    - MPI_Graph_create（集中式）
    - MPI_Dist_graph_create（分布式但可描述任意边）
- 该接口进一步**约束输入**，以换取：
    - 更低的构建通信开销
    - 更贴近局部通信视角
 
**核心原则**

- **每个** **MPI process** **只描述与自己相关的** **edges**
- 不需要，也不允许描述与自身无关的连接
- 因此：
    - 不需要“告知”其他 process 额外拓扑信息
    - 构建阶段更高效

    - 因此可以查询 **任意** **rank** **的** **connectivity**
- 在 distributed graph 中：
    - graph 信息是 **分布式存储**
    - 每个 MPI process **只知道与自己相关的部分**
    - 因此：
        - **只能查询自己的** **connectivity**
        - 无法查询其他 MPI process 的邻居信息

这是设计上的必然结果，也是 scalability 的代价。
 
**MPI_Dist_graph_neighbors_count**  
获取自身的邻居数量  
**函数原型**

![Exported image](Exported%20image%2020260730161026-70.png)

int MPI_Dist_graph_neighbors_count(￼ MPI_Comm comm,￼ int* in_degree,￼ int* out_degree,￼ int* weighted￼);
 
**参数说明**

- comm￼一个 distributed graph communicator
- in_degree￼当前 MPI process 的 **入边数量**
- out_degree￼当前 MPI process 的 **出边数量**
- weighted￼指示 graph 是否为 weighted graph￼返回非零表示存在权重
 
**使用目的**

- 在不知道 neighbour 数量的情况下：
    - 先查询 in-degree / out-degree
- 为后续 neighbour 数组分配合适内存空间
 
**MPI_Dist_graph_neighbors**  
获取自身的邻居列表  
**函数原型**

![Exported image](Exported%20image%2020260730161029-71.png)

int MPI_Dist_graph_neighbors(￼ MPI_Comm comm,￼ int max_in_degree,￼ int sources[],￼ int source_weights[],￼ int max_out_degree,￼ int destinations[],￼ int destination_weights[]￼);
 
**参数说明**

- comm￼distributed graph communicator
- max_in_degree￼可容纳的入边数量￼通常来自 MPI_Dist_graph_neighbors_count
- sources[]￼所有指向当前 MPI process 的 source ranks
- source_weights[]￼入边权重数组￼若 graph 为 unweighted，可忽略
- max_out_degree￼可容纳的出边数量
- destinations[]￼当前 MPI process 指向的 destination ranks
- destination_weights[]￼出边权重数组
 
**标准使用流程总结**  
在 distributed graph topology 中，推荐的 neighbour 查询流程是：

1. 调用 MPI_Dist_graph_neighbors_count
    - 获取 in-degree 与 out-degree
2. 根据返回值分配：
    - sources / destinations 数组
3. 调用 MPI_Dist_graph_neighbors
    - 获取实际 neighbour 列表
