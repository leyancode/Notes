# Fixture 与 Mock 的区别（测试替身 Test Double）

## 1. 这个问题在面试中考什么？

考的是你能不能分清「测试的**前置环境**」和「被替换的**依赖**」——这是写单元测试的基本功。

> [!important]- 必须掌握
> 后端 / Agent / 任何写单测的岗位都会问「你怎么测一个依赖外部服务（数据库、LLM、网络）的函数」。答这题必然用到 fixture 和 test double，能不能把两者分清、能不能说出 stub/fake/mock 的差别，直接暴露你是「跟着模板写测试」还是「理解测试在保护什么」。

## 2. 重要程度总览

一句话：**fixture 是搭台子（环境/数据），mock 是换演员（依赖），两者正交，常一起用。**

> [!info]- 需要掌握
> - **Fixture（夹具）**：必须掌握——pytest 写测试天天用。
> - **Mock vs Stub vs Fake（测试替身家族）**：必须能区分 stub / fake / mock 三个高频词。
> - **Spy / Dummy**：了解即可，知道它们属于同一家族、各占一个位置即可。

## 3. 核心知识表格

先看主对比，再看测试替身家族的完整分类。

> [!summary]- Fixture vs Mock 核心对比
> | 维度 | Fixture（夹具） | Mock（模拟对象） |
> |---|---|---|
> | 关注点 | 测试运行的**前置环境 / 数据 / 状态** | **替换真实依赖** + 验证它被怎么调用 |
> | 回答的问题 | "在什么条件下测" | "把哪个依赖换成可控替身" |
> | 关注状态还是行为 | 状态（state） | 行为（behavior verification） |
> | 典型形态 | pytest `@fixture` 提供 temp dir / DB 连接 / 样例对象 | 记录调用参数，断言"被调用过、且参数是 X" |
> | 生命周期 | setup → 测试用 → teardown（自动清理） | 测试内构造，测完检查交互 |
> | 是不是同一维度 | 否——fixture 可以**提供**一个 mock，二者正交 | 否——mock 只是 fixture 可能返回的东西之一 |

> [!info]- 测试替身家族（Test Double，Meszaros 分类）
> "mock" 常被当成所有替身的统称，精确说它只是其中一种。
> | 类型 | 做什么 | 验证交互？ | 项目/常见例子 |
> |---|---|---|---|
> | Dummy | 只占位填参数，从不真正使用 | 否 | 一个必填但用不到的参数 |
> | Stub | 返回**预设值**，喂给被测代码 | 否 | `dict_router`（查表返回固定输出） |
> | Fake | 有**简化但能工作**的真实现 | 否 | `FakeLLM`（内存版 SDK 客户端）、内存数据库 |
> | Spy | 记录"被怎么调用了"供事后检查 | 事后可查 | 手写一个记录调用次数的对象 |
> | Mock | 预设**期望** + 自动**验证**调用方式 | 是 | `unittest.mock.Mock` |

## 4. 高频问题整理

### 4.1 Fixture 到底是什么、名字为什么这么叫？

Fixture 是把被测对象放进一个**固定、已知、可重复**的初始环境的那套准备代码。

> [!important]- 必须掌握
> 名字来自制造业的「工装夹具」——车间里把工件**固定在同一位置**、让你每次都能在**完全相同的条件下**加工/测量的装置。软件 fixture 同理：它把测试的前置状态（数据、临时文件、DB 连接、样例对象）固定下来，保证每次测试跑在**同样的起点**上，测试才可重复、可信。

> [!question]- 面试怎么答
> "Fixture 是测试的前置环境准备。比如 pytest 里用 `@pytest.fixture` 造一个临时目录或一份样例数据，多个测试共享它、跑完自动清理。它保证每个测试从**相同的已知状态**开始——名字就来自制造业里固定工件的夹具。"

> [!example]- 具体例子
> ```python
> @pytest.fixture
> def sample_questions():
>     return [{"question": "q1", "intent": "best_config", "unknowns": 1000000}]
>
> def test_scoring(sample_questions):   # 参数名 = fixture 名，pytest 自动注入
>     score = score_router(some_router, sample_questions)
>     assert score["accuracy"] == 1.0
> ```
> `sample_questions` 就是 fixture：提供**数据/状态**，本身不替换任何依赖。

### 4.2 Mock 和 Stub 的区别是什么？（最高频的追问）

Stub 只**给状态**（返回预设值），Mock 还要**验证行为**（断言"你确实按这个方式调用了我"）。

> [!important]- 必须掌握
> 这是面试区分度最高的一刀。**Stub = state verification**：我准备好假的返回值，让被测代码跑下去，最后只检查**被测代码的输出对不对**。**Mock = behavior verification**：我不光给返回值，还要在测试结尾断言**这个依赖被调用了几次、参数是什么**——测的是"交互对不对"。选哪个取决于你要验证的是**结果**还是**交互**。

> [!question]- 面试怎么答
> "Stub 和 Mock 都是测试替身，区别在验证什么。Stub 提供预设返回值，我只断言被测函数的**输出**——这叫状态验证。Mock 除了返回值，还会记录并断言**它是怎么被调用的**（次数、参数）——这叫行为验证。举例：测'下单后有没有发通知'，我会用 mock 断言 `notify.send` 被调用了一次、收件人正确；如果只是测'下单金额算得对不对'，一个返回固定运费的 stub 就够了。"

> [!example]- 具体例子
> ```python
> # Stub：只给返回值，验证输出（状态）
> stub = lambda q: {"intent": "best_config", "unknowns": 1000000}
> assert score_router(stub, qs)["accuracy"] == 1.0   # 断言的是"结果"
>
> # Mock：验证交互（行为）
> m = unittest.mock.Mock(return_value={"intent": "best_config", "unknowns": 1000000})
> score_router(m, qs)
> m.assert_called_once_with("q1")   # 断言的是"它被怎么调用"
> ```

### 4.3 Fake 又是什么？和 Stub 怎么分？

Fake 是**简化但真的能运行**的替身；Stub 是**写死返回值、没有内部逻辑**的替身。

> [!info]- 需要掌握
> Stub 的返回是**硬编码**的（问 q1 就返回这个 dict，没有逻辑）；Fake 有**真实的内部实现**，只是为了测试而简化。经典例子：用内存字典冒充数据库——它真的支持 put/get、真有逻辑，只是不落盘。你项目里的 `FakeLLM` 就是 fake：它模拟了 SDK 客户端的接口和调用流程，只是把"模型返回什么"改成构造时注入，而不是真发请求。

> [!question]- 面试怎么答
> "Fake 是有真实逻辑但简化的实现，Stub 是写死返回值的。比如内存数据库是 fake（真能存取，只是不落盘），而'调 getUser 永远返回同一个假用户'是 stub。我项目里 LLM 客户端的替身是 fake——它复刻了 SDK 的接口，只把网络请求换成注入的预设响应，所以测试完全离线、确定。"

## 5. 对比关系或流程梳理

一张图理清：fixture 是外层容器，测试替身是它可能装的内容之一。

> [!summary]- 两者正交、如何组合
> ```
> ┌─────────────── Fixture（搭台子：环境/状态/资源） ───────────────┐
> │  可能提供：样例数据、临时目录、DB 连接、……                       │
> │  也可能提供：一个 Test Double（换演员）                          │
> │        └── Dummy / Stub / Fake / Spy / Mock 五选一              │
> └────────────────────────────────────────────────────────────────┘
> ```
> - **Fixture 回答"环境"**，Test Double 回答"依赖"，两个问题，不冲突。
> - 常见组合：`@pytest.fixture def fake_client(): return FakeLLM(...)`——**用 fixture 提供一个 fake**。
> - 所以「fixture vs mock」这个问法本身略有误导：它们不是二选一，而是"外壳 vs 外壳里可能装的一种东西"。

## 6. 常见误区

> [!warning]- 常见误区
> - **把所有测试替身都叫 mock**：日常口语可以，面试里被追问 stub/mock 区别时要能精确区分（状态 vs 行为验证）。
> - **以为 fixture 和 mock 二选一**：错。二者正交，fixture 常常**返回**一个 mock/fake。
> - **过度 mock**：把被测逻辑周围全 mock 掉，测试只验证"我调用了我 mock 的东西"，一改实现就红、且抓不到真 bug（脆弱测试）。**能用 stub/fake 就别用 mock**——只在"交互本身是被测行为"（发通知、扣款）时才用 mock 验证调用。
> - **fixture 忘了 teardown/隔离**：fixture 之间共享可变状态、不清理，会导致测试互相污染、顺序相关——违背"每个测试从相同已知状态开始"。
> - **混淆 Fake 和 Stub**：Fake 有真实逻辑（内存 DB），Stub 是写死返回值。你项目的 `FakeLLM` 是 fake，`dict_router` 是 stub。

## 7. 面试口述版答案

> [!question]- 30 秒完整口述
> "Fixture 和 mock 其实不在一个维度。**Fixture 是测试的前置环境**——用 pytest 的 `@fixture` 提供样例数据、临时目录、连接这些，保证每个测试从相同的已知状态开始，名字来自制造业固定工件的夹具。**Mock 属于'测试替身'家族**，是用来替换真实依赖的假对象。这个家族里：stub 只返回预设值、验证的是被测代码的**输出**（状态验证）；fake 有简化但能跑的真实现，比如内存数据库；mock 更进一步，还会**断言依赖被怎么调用**（行为验证）。两者常一起用——我经常用一个 fixture 去**提供**一个 fake 客户端。比如我给 LLM router 写测试，就是用 fixture 注入一个 FakeLLM，让整套测试离线、确定、不烧 key。选替身的原则是能用 stub/fake 就别用 mock，只有当'有没有正确调用某依赖'本身就是要测的行为时才上 mock。"

## 9. 最终速记版

> [!tip]- 一句话记忆
> **Fixture 搭台子（环境/状态），Test Double 换演员（依赖）。**
> 换演员分五档，只需记高频三个：
> - **Stub** = 给台词（预设返回值），验**结果**
> - **Fake** = 简化版真演员（内存 DB / FakeLLM），能真跑
> - **Mock** = 给台词 + 查岗（验证被怎么调用），验**行为**
> 口诀：**Stub 看输出，Mock 看调用，Fake 有真身；Fixture 管环境，替身管依赖。**
